# Graceful shutdown — going down without losing requests

Rollouts, scale-downs and node drains all end with "delete one pod". Here we follow the order in which that pod goes down without losing the requests it was handling. The full rollout flow is in [Zero-Downtime Deploys (Rolling Update)](../k8s/rolling-update.mdx), and node maintenance is in [Draining Nodes and Upgrading the Cluster](../k8s/node-drain.mdx).

## Shutdown order at a glance

| Step | What happens | What the app or config must do |
| --- | --- | --- |
| 1 | The pod becomes Terminating and the grace period starts | Raise `terminationGracePeriodSeconds` for long tasks (default 30s) |
| 2 | Removal from the request targets and stopping start at the same time | Design assuming the order is not guaranteed |
| 3 | The `preStop` hook runs | Wait a few seconds so the target removal can spread |
| 4 | SIGTERM arrives | Stop accepting new requests, finish in-flight ones, exit on its own |
| 5 | After the grace period, SIGKILL forces a stop | At this point, in-flight requests fail |

Set `terminationGracePeriodSeconds` and `preStop` in the pod template `spec`. Check the applied values with `kubectl get pod <name> -o yaml`.
