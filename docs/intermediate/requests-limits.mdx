# Requests and limits

Each container declares resources as two values: "I need at least this much" (requests) and "I can never use more than this" (limits). Here we follow how each value is used at placement time and at run time. The detailed way the scheduler filters and picks nodes is in [Which Node Gets the Pod (Scheduling)](../k8s/scheduling.mdx).

## Myths and facts

| Myth | Fact |
| --- | --- |
| Low usage means there is room for a pod | The scheduler only looks at request totals. When allocation is full, it is `Pending` regardless of usage |
| Going over the limit kills the container, CPU or memory | CPU is only slowed (throttling); only memory is killed (`OOMKilled`) |
| Requests can be left empty | Placement goes wrong, creation is rejected in namespaces with quotas, and the HPA cannot compute utilization |
| HPA CPU 80% means 80% of the limit | It is measured against requests |
| Generous requests are safer | Pods fail to place even with room, and resources are wasted |
