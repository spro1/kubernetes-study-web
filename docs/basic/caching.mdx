## Caching patterns

| Pattern | Read | Write | Good for | Watch out |
|---|---|---|---|---|
| Cache-aside (lazy loading) | App checks cache, loads DB on miss, fills cache | App writes DB, deletes the key | Most read-heavy apps; the cache can fail without losing data | First read after a miss or a restart is slow; stale window until TTL |
| Read-through | The cache layer loads the DB on a miss for the app | Usually combined with write-through | Keeping load logic out of app code | Needs a cache library or product that knows how to load from the DB |
| Write-through | Reads hit a cache that is always filled | Every write goes to cache and DB together | Data read right after it is written | Writes are slower; caches data that may never be read |
| Write-behind (write-back) | Reads hit the cache | Write to cache now, flush to DB later in batches | Very high write rates, such as counters | Data written to the cache but not yet flushed is lost if the cache dies |

## Try it yourself

```bash
redis-cli SET product:42 '{"price":100}' EX 300   # Store with a 300 s TTL
redis-cli GET product:42                           # Hit: returns the value
redis-cli TTL product:42                           # Seconds left (-1 no TTL, -2 no key)
redis-cli EXPIRE product:42 60                     # Change the TTL
redis-cli DEL product:42                           # Invalidate after a write
redis-cli SET lock:product:42 1 NX EX 5            # Stampede lock: only the first caller gets OK
redis-cli INFO stats | grep -E 'keyspace_(hits|misses)|evicted_keys'   # Hit ratio and evictions
redis-cli CONFIG GET maxmemory-policy              # What happens when memory is full
```

`valkey-cli` takes the same commands.
