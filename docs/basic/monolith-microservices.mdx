# Monolith, Modular Monolith and Microservices

A shop starts as one application. As it grows, someone suggests splitting it into services. Follow the same **checkout** request through a **monolith**, a **modular monolith** and **microservices**, and see what each split buys you and what it costs.

## Gains and costs

| | Monolith | Modular monolith | Microservices |
|---|---|---|---|
| Deploy unit | One | One | One per service |
| Internal calls | Function calls | Function calls through module interfaces | Network calls (HTTP, gRPC, events) |
| Data | One database, shared tables | One database, tables owned per module | Database per service |
| Transactions | Local, across everything | Local, across modules | Only inside a service; sagas across |
| Scaling | Whole app | Whole app | Per service |
| Team independence | Low | Medium | High, if data and APIs are separate |
| Debugging | One process, one log | One process, one log | Distributed tracing needed |
| Ops cost | Low | Low | High: pipelines, dashboards, on-call per service |

## Try it yourself

```bash
# Availability of a chain: 5 required services at 99.9% each
python3 -c 'print(round(0.999**5 * 100, 2), "%")'        # about 99.5%

# Chance that a request needing 10 calls hits at least one 1%-slow call
python3 -c 'print(round((1 - 0.99**10) * 100, 1), "%")'  # about 9.6%

# How many deploy units, and does each ship on its own?
kubectl get deploy -n shop
kubectl rollout history deploy/payments -n shop

# Do services share a database? Compare the DB host each one is given
kubectl get deploy -n shop -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.template.spec.containers[*].env[?(@.name=="DB_HOST")].value}{"\n"}{end}'

# How long does one checkout take end to end?
curl -s -o /dev/null -w 'total %{time_total}s\n' https://shop.example.com/checkout
```
