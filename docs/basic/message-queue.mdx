# How a Message Queue Decouples Services

The order service publishes one **event**. Shipping and email each read it at their own pace. Follow the event through **producer → topic partition → consumer group → offset commit**, then watch what happens when a consumer crashes, falls behind, or hits a message it can never process.

## Delivery guarantees

| Guarantee | How you get it | What a crash does | Use it for |
|---|---|---|---|
| At-most-once | Commit the offset before processing | The message can be lost | Data where a gap is fine, such as some sampled metrics |
| At-least-once | Commit the offset after processing | The message can be processed twice | The usual default. Pair it with an idempotent consumer |
| Exactly-once | Kafka idempotent producer plus transactions, consumers with `isolation.level=read_committed` | Read-process-write inside Kafka happens once | Stream processing from Kafka topic to Kafka topic. Side effects outside Kafka, such as an email or a payment call, still need an idempotency key |

## Try it yourself

```bash
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders \
  --partitions 3 --replication-factor 3                      # needs 3 brokers
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders   # Leader, Replicas, Isr per partition
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders \
  --property parse.key=true --property key.separator=:        # type: order-42:created
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders \
  --group shipping --from-beginning --property print.key=true --property print.partition=true
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group shipping   # CURRENT-OFFSET, LOG-END-OFFSET, LAG
```

Run two consumers with the same `--group` and they split the partitions. Run one with a different group and it gets every message again.
