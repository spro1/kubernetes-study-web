# Distributed Systems Basics

On one machine, a function call either returns or throws. Across a network there is a third answer: silence. Follow one order through **client → order service → database and replica → outbox → queue → shipping**, and meet the problems every cloud system has, with the plain patterns that handle them.

## Problem → pattern

| You meet | Why it happens | Pattern |
|---|---|---|
| Timeout, unsure if the write happened | Lost reply, slow node, partial failure | Idempotency key, safe retries with backoff |
| Duplicate messages | At-least-once delivery, retries after crashes | Event ids, idempotent consumers |
| Just-written data missing on read | Async replication lag | Read-your-writes: read from primary, or wait for the replica to catch up |
| Two sides of a split both accept writes | No majority rule | Quorum-based consensus (Raft in etcd), odd member count |
| Newer update lost | Ordering by wall-clock timestamps | Version numbers, optimistic concurrency (409 Conflict) |
| Order saved but event never sent | Dual write to DB and broker | Transactional outbox plus relay |

| Model | A read may return | Typical use |
|---|---|---|
| Strong (linearizable) | Only the latest completed write | Leader election, locks, balances |
| Read-your-writes | Your own writes for sure; others' maybe later | User profile, "my orders" |
| Eventual | Old data for a while; copies converge | Caches, search indexes, feeds |

## Try it yourself

```bash
# Optimistic concurrency in Kubernetes: an update based on an old resourceVersion fails
kubectl create configmap demo --from-literal=count=1
kubectl get configmap demo -o yaml > old.yaml                      # remembers the current resourceVersion
kubectl patch configmap demo -p '{"data":{"count":"2"}}'            # someone else changes it
kubectl replace -f old.yaml                                         # Conflict: the object has been modified
kubectl delete configmap demo

# Replication lag in PostgreSQL
psql -h primary -c "SELECT client_addr, state, replay_lag FROM pg_stat_replication;"
psql -h replica -c "SELECT now() - pg_last_xact_replay_timestamp() AS lag;"

# How far is this machine's clock off? (chrony or systemd-timesyncd)
chronyc tracking            # "System time" shows the offset from NTP
timedatectl                 # "System clock synchronized: yes/no"

# A retry with an idempotency key (header name depends on the API)
curl -X POST https://api.example.com/orders \
  -H 'Idempotency-Key: 6f1c2a9e-order-42' -d '{"item":"book"}'
```
