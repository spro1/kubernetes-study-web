# SLOs and Alert Design

A "CPU over 80%" alert fires 30 times a day, yet users have no complaints. Meanwhile, users may hit errors with no alert at all. Let's redesign the alerts that wake people up around user experience, and follow how to narrow down the cause once one fires.

## Cause-based vs symptom-based alerts

| Type | Example | Result | Where it belongs |
| --- | --- | --- | --- |
| Cause-based | CPU over 80%, Pod restarted once | Fires even without user impact, causing alert fatigue | Dashboards and analysis |
| Symptom-based | Error budget burn rate, p99 latency over 2s for 10 minutes | Fires only for problems users actually feel | Alerts that wake people |

With Prometheus, write alert conditions as alerting rules, and set grouping, repeat intervals and receivers in Alertmanager.

## Try it yourself

```bash
kubectl get --raw /metrics | grep '^apiserver_request_total' | head    # Request counts by code: raw material for an SLI
curl -s <prometheus>/api/v1/query --data-urlencode 'query=sum(rate(apiserver_request_total{code=~"5.."}[5m])) / sum(rate(apiserver_request_total[5m]))'   # Error ratio over 5 minutes
kubectl get prometheusrules -A                                         # Alerting rules (Prometheus Operator)
curl -s <prometheus>/api/v1/rules | jq '.data.groups[].rules[].name'   # Rules Prometheus actually loaded
curl -s <alertmanager>/api/v2/alerts/groups                            # Alerts grouped into notifications
```
