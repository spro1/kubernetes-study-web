# Audit Logs

"Who read the production database password yesterday?" To answer that, a record must be left as the request passes through. Let's follow what the Kubernetes API server's audit log records, at what level, and where it is sent for keeping. The gates a request passes inside the API server are covered first in [How an API Request Gets Stored](./api-request-path.mdx).

## Levels at a glance

| Level | What is recorded | When to use |
| --- | --- | --- |
| None | Nothing | Frequent requests with no audit value |
| Metadata | Who, when, on what, which verb, result | Resources with secrets in the body, like Secrets |
| Request | Above + request body | Changes where what they tried to change matters |
| RequestResponse | Above + response body | Only where truly needed. Large storage, and secrets may be kept |

## Try it yourself

```bash
kubectl get pod -n kube-system -l component=kube-apiserver -o yaml | grep audit   # Is an audit policy and log path set?
sudo cat <audit-policy-file>                                    # Rule order and level per resource
sudo grep '"resource":"secrets"' <audit-log-file> | tail -n 3   # Who read which Secret, and when
sudo grep '"resource":"secrets"' <audit-log-file> | grep -c '"level":"RequestResponse"'   # Should be 0: no secret values in the log
kubectl auth can-i get secrets -n <namespace> --as=<user>       # Did that user really need read access?
```
