# Leader Election with Leases

kube-controller-manager, kube-scheduler and most operators run several replicas for availability, but only one may act at a time. They agree on who that is with a small Lease object in the API server. Follow how the Lease is taken, renewed, lost and taken over.

## The three timings

| Setting (client-go name) | What it controls | kube-controller-manager default | If set too low | If set too high |
|---|---|---|---|---|
| `leaseDuration` | How long followers wait without a renewal before taking over | 15 s | Leadership flaps on short API hiccups | Slow failover after a crash |
| `renewDeadline` | How long the leader keeps trying to renew before giving up | 10 s | Leader steps down on brief API slowness | Less margin before followers may take over |
| `retryPeriod` | How often the leader renews and followers retry | 2 s | More writes to the API server | Renewals may miss the deadline |

The flags are `--leader-elect-lease-duration`, `--leader-elect-renew-deadline` and `--leader-elect-retry-period` on kube-controller-manager and kube-scheduler. Keep `leaseDuration` > `renewDeadline` > `retryPeriod`.

## Try it yourself

```bash
kubectl get lease -n kube-system                     # HOLDER for controller-manager, scheduler, and more
kubectl get lease kube-controller-manager -n kube-system -o yaml   # holderIdentity, leaseDurationSeconds, renewTime, leaseTransitions
kubectl get lease kube-scheduler -n kube-system \
  -o jsonpath='{.spec.holderIdentity}{"\n"}'         # Which instance schedules right now
kubectl get lease -n kube-system -w                  # Each update line is a renewal or takeover
kubectl get lease -n kube-node-lease                 # One heartbeat Lease per node
kubectl get lease <node-name> -n kube-node-lease \
  -o jsonpath='{.spec.renewTime}{"\n"}'              # Last kubelet heartbeat
kubectl get leasecandidates -n kube-system           # Only if coordinated leader election is enabled
```
