# Backing Up and Restoring a Cluster

A cluster keeps state in several places, and each place needs its own backup. Follow an **etcd snapshot** and a **Velero backup** from the source cluster to object storage, and back into a new cluster.

## What each method covers

| Method | API objects | Volume data | Scope | Good for |
|---|---|---|---|---|
| etcd snapshot | All, at one moment | No | Whole cluster | Losing the control plane |
| Velero (objects only) | Selected namespaces or labels | No | Namespace, label | Deleted resources, migration |
| Velero + CSI snapshots | Yes | Yes, in the same storage system | Namespace | Fast restore in the same region |
| Velero + data mover or File System Backup | Yes | Yes, copied to the bucket | Namespace | Restore in another region or cluster |
| Database dump or replication | No | The database only, consistent | One database | Databases, point-in-time recovery |
| Git (GitOps) | Manifests you wrote | No | Whatever is in the repo | Rebuilding config, not data |

## Try it yourself

```bash
# etcd snapshot (kubeadm paths; run on a control plane node)
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /backup/snapshot.db
etcdutl --write-out=table snapshot status /backup/snapshot.db   # Hash, revision, keys, size

# Velero
velero backup create shop-test --include-namespaces shop --wait
velero backup describe shop-test --details        # Objects, volume snapshots, warnings
velero backup logs shop-test | grep -i error
velero restore create --from-backup shop-test --namespace-mappings shop:shop-restore-test   # Restore beside the original
velero restore describe <restore-name>            # Skipped and failed items
```
