# Managed Kubernetes — Who Runs What

With managed Kubernetes (for example Amazon EKS, Google GKE or Azure AKS), the cloud provider runs the control plane and you run the worker nodes. Follow one team from `kubectl` login to a running, exposed, autoscaled app, and see where Kubernetes hands work to the cloud.

## Who manages what

| Part | Provider | You |
|---|---|---|
| API server, etcd, scheduler, controller manager | Runs, patches, backs up, scales | Choose version and tier, enable control-plane logs |
| Control-plane version | Releases versions, may force upgrades at end of support | Trigger upgrades, check deprecated APIs |
| Worker nodes | Provides node images and managed node groups or pools | Choose size, count, OS image, upgrade timing (less in Auto Mode or Autopilot) |
| Networking | Provides the CNI and the cloud LB integration | VPC, subnets, IP ranges, security groups, NetworkPolicy |
| Access | Verifies cloud identity | Map identities to RBAC, grant least privilege |
| Workloads, Secrets, data | — | Everything: manifests, backups of volumes, app security |

Names differ by provider:

| Concept | EKS | GKE | AKS |
|---|---|---|---|
| Group of worker VMs | Managed node group | Node pool | Node pool |
| kubectl login helper | `aws eks get-token` | `gke-gcloud-auth-plugin` | `kubelogin` |
| Cloud identity → RBAC | Access entries | IAM + RBAC | Microsoft Entra ID + RBAC |
| Pod → cloud role | IRSA, EKS Pod Identity | Workload Identity Federation for GKE | Microsoft Entra Workload ID |
| Provider runs the nodes too | EKS Auto Mode | Autopilot | AKS Automatic |

## Try it yourself

```bash
aws eks update-kubeconfig --name demo --region ap-northeast-2   # Writes kubeconfig with the token helper (EKS example)
kubectl config view --minify                         # See the exec plugin instead of a password
kubectl auth whoami                                  # The Kubernetes user your cloud identity maps to
kubectl get nodes -L topology.kubernetes.io/zone,node.kubernetes.io/instance-type   # Nodes are VMs in zones
kubectl get svc -A --field-selector spec.type=LoadBalancer   # Services that created cloud LBs
kubectl get pv -o custom-columns=NAME:.metadata.name,ZONE:.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values   # Which zone each disk is in
kubectl get events -A --field-selector reason=FailedScheduling   # Pending Pods the autoscaler should see
kubectl version                                      # Client and control-plane versions
```
