# Upgrading a cluster with kubeadm (CKA)

This relates to "Manage the lifecycle of Kubernetes clusters (upgrades)" in the CKA Cluster Architecture, Installation and Configuration (25%) domain. We upgrade a 1.36 cluster built with kubeadm (the official Kubernetes install tool) to 1.37, and follow which commands run on each node, in what order.

Why the control plane goes first, and how drain respects PDBs, are covered in [Draining Nodes and Upgrading the Cluster](../k8s/node-drain.mdx). Here we focus on the order of kubeadm commands.

## Common exam questions

| Situation | What to do / command | Trap |
| --- | --- | --- |
| Upgrade the control plane by one version | Switch repo address → install kubeadm → `kubeadm upgrade plan` → `kubeadm upgrade apply v1.37.x` | You cannot skip minor versions. With the old repo address, the new packages do not show up |
| Second control plane node | `kubeadm upgrade node` | `upgrade apply` runs only once, on the first node |
| apply finished but the node version did not change | Install kubelet and kubectl → `systemctl daemon-reload` → `systemctl restart kubelet` | VERSION in `kubectl get nodes` is the kubelet version |
| Upgrade a worker node | Install kubeadm → `kubeadm upgrade node` → `kubectl drain <node> --ignore-daemonsets` → install and restart kubelet → `kubectl uncordon <node>` | Do not run `upgrade apply` on a worker. Run drain where kubectl is available, and install packages on the node itself |
| The job is done | `kubectl uncordon`, then check Ready and VERSION with `kubectl get nodes` | Forget uncordon and the node stays SchedulingDisabled |
