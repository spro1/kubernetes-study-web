# Node NotReady and component failures (CKA)

This relates to troubleshooting "clusters and nodes" and "cluster components" in the CKA Troubleshooting (30%) domain. We work through two scenes: a worker node turning NotReady, and the control plane API server dying so that even kubectl stops answering.

How pods get recreated on other nodes when a node stops is in [When a Pod Dies (Self-Healing)](../k8s/self-healing.mdx), and how expired certificates cut communication is in [Cluster Certificate Expiry](../advanced/cluster-cert.mdx). Here we focus on the order of finding the cause from inside the node.

## Common exam questions

| Situation | What to do / command | Trap |
| --- | --- | --- |
| A node is NotReady | `kubectl describe node <node>` → `ssh <node>` → `systemctl status kubelet` → `journalctl -u kubelet` | Do not read logs on the control plane node. Log in to the problem node |
| The kubelet is off | `systemctl start kubelet`, `systemctl enable kubelet` | Forget enable and it is NotReady again after a reboot |
| You edited the kubelet config file | `systemctl daemon-reload` → `systemctl restart kubelet` | Editing without restarting does not take effect |
| kubectl says connection refused | On the control plane node: `crictl ps -a`, `crictl logs <container ID>` | `kubectl logs` needs the API server to work |
| A static pod config is wrong | Edit the file under `/etc/kubernetes/manifests/` directly | `kubectl edit` or `kubectl delete` cannot fix it. Only editing the file makes the kubelet recreate it |
