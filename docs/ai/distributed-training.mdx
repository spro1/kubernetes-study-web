# Training One Model on Many GPUs

One training run spread over 4 GPUs on 2 nodes. Follow how each GPU gets its own slice of the data, how gradients are combined every step, how sharding fits a bigger model, and what happens when one worker dies. How the Job waits for GPU quota is in [From Training Job to Model](../ai/training-job.mdx).

## Choosing a parallelism

| Approach | What each GPU holds | Communication | Use when |
| --- | --- | --- | --- |
| DDP (data parallel) | Full model, gradients, optimizer state | All-reduce of gradients once per step | The model and its optimizer state fit on one GPU |
| ZeRO-1 / ZeRO-2 | Full weights, shard of optimizer state (and gradients) | About the same as DDP | Optimizer state is what does not fit |
| FSDP / ZeRO-3 | A shard of weights, gradients and optimizer state | All-gather of weights, reduce-scatter of gradients, about 1.5× DDP | Even the weights plus states do not fit on one GPU |
| Tensor parallel | A slice of every layer | Collectives inside every layer | Layers are too large; keep inside one node on NVLink |
| Pipeline parallel | A range of layers | Activations between stages | The model is too deep for one node; needs micro-batches |

## Try it yourself

```bash
kubectl get clustertrainingruntimes                       # Runtimes a TrainJob can use, e.g. torch-distributed
kubectl get trainjobs -n <namespace>                      # Kubeflow Trainer v2 jobs
kubectl get jobset -n <namespace>                         # The JobSet the TrainJob created
kubectl get pods -n <namespace> -l jobset.sigs.k8s.io/jobset-name=<trainjob> -o wide   # One Pod per node
kubectl logs -n <namespace> <pod> | grep -E "NCCL INFO|rank"   # With NCCL_DEBUG=INFO set: transports and rings
kubectl exec -n <namespace> <pod> -- nvidia-smi topo -m   # NVLink vs PCIe between the GPUs in a node
# Inside a container: one process per GPU, two nodes, rendezvous at the rank 0 Pod
torchrun --nnodes=2 --nproc-per-node=2 --rdzv-backend=c10d --rdzv-endpoint=<rank0-host>:29400 --rdzv-id=run1 train.py
```
