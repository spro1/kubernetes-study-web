# LLM 추론 오토스케일링

[부하에 맞춰 늘어나기 (HPA)](../k8s/autoscaling.mdx)의 HPA는 CPU를 보는 웹 파드에는 잘 맞는다. LLM 레플리카는 다르다. GPU는 늘 바빠 보이고, 새 레플리카는 뜨는 데 몇 분이 걸리며, 너무 일찍 내리면 답변이 스트리밍 도중 끊긴다. 트래픽 급증 한 번을 따라가며 무엇을 보고 늘려야 하는지, 지연은 어디서 생기는지 본다.

| CPU 사용률 | 아니다 | 엔진은 대부분 GPU를 기다리므로 사용자가 줄을 서도 CPU는 낮다 |
| GPU 사용률(예: `DCGM_FI_DEV_GPU_UTIL`) | 아니다 | 커널이 돈 시간의 비율이라, 요청 하나만 디코드해도 100% 가까이 나온다 |
| 대기 요청(`vllm:num_requests_waiting`) | 맞다, 주 신호 | 레플리카가 배치에 요청을 더 못 넣는 순간 바로 오른다 |
| KV 캐시 사용률(`vllm:kv_cache_usage_perc`) | 맞다, 조기 경보 | 100% 가까우면 새 요청이 기다리거나 진행 중인 요청이 밀려난다 |
| TTFT p95(`vllm:time_to_first_token_seconds`) | SLO·알림용 | 사용자가 느끼는 값이지만 이미 기다린 뒤에야 움직인다 |
| 초당 요청 수 | 약하다 | 프롬프트와 답변 길이가 제각각이라 같은 수치가 가벼울 수도 무거울 수도 있다 |

## 직접 확인해 보기

```bash
kubectl port-forward deploy/llm 8000:8000 &
curl -s localhost:8000/metrics | grep -E '^vllm:(num_requests_waiting|num_requests_running|kv_cache_usage_perc)'   # 엔진 자신의 부하
kubectl get hpa -w                                   # 부하에 따라 TARGETS(현재/목표)와 REPLICAS가 바뀌는 것
kubectl describe hpa keda-hpa-llm                    # 지표 값, 이벤트, 늘거나 늘지 않은 이유
kubectl get scaledobject                             # KEDA: READY와 ACTIVE
kubectl get pods -l app=llm -w                       # Pending(GPU 노드 없음) → Running → Ready(모델 적재 완료)
```

대기 요청으로 늘리는 KEDA `ScaledObject`:

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: llm
spec:
  scaleTargetRef:
    name: llm                  # vLLM Deployment
  minReplicaCount: 1           # 0이면 0까지 줄이고, 깨울 때 콜드 스타트
  maxReplicaCount: 8
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleDown:
          stabilizationWindowSeconds: 600   # 천천히 줄인다
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring:9090
        query: sum(vllm:num_requests_waiting{model_name="chat"})
        threshold: "5"         # 레플리카당 대기 요청 목표
```
