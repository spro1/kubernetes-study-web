# 요청을 어느 레플리카로 보낼까 (추론 라우팅)

같은 모델을 레플리카 여러 개로 실행하면, 요청마다 어느 레플리카로 보낼지 정해야 한다. 일반 웹 서비스는 돌아가며 보내면 충분하지만, LLM은 요청마다 길이가 크게 다르고 레플리카마다 **이미 계산해 둔 앞부분(프리픽스 캐시)** 이 다르다. 그래서 입구 뒤에 레플리카 상태를 보고 고르는 **분배기(EPP, Endpoint Picker)** 를 둔다.

## 쿠버네티스에서는

Gateway API 추론 확장에서는 같은 모델의 레플리카 묶음을 **InferencePool**(inference.networking.k8s.io/v1)로 정의하고, 그 묶음에 붙은 분배기(EPP)가 요청마다 레플리카를 고른다. 입구는 이 확장을 지원하는 게이트웨이 구현을 쓴다. llm-d 같은 프로젝트는 이 구조 위에 프리픽스 캐시·부하 기반 점수 규칙을 더하고, 프리필·디코드 분리 서빙에서는 프리필 쪽과 디코드 쪽 레플리카를 함께 고른다. 프리픽스 캐시가 무엇인지는 [KV 캐시가 차오르기까지](../llm/kv-cache.mdx)에서, 분리 서빙은 [읽는 곳과 쓰는 곳 나누기 (프리필·디코드 분리)](../llm/pd-disaggregation.mdx)에서 본다.

## 직접 확인해 보기

```bash
kubectl get inferencepools -A                        # 모델별 레플리카 묶음 (InferencePool)
kubectl describe inferencepool <이름> -n <네임스페이스>   # 파드 선택 조건과 붙은 EPP
kubectl get httproutes -n <네임스페이스>                # 묶음을 가리키는 게이트웨이 경로
curl -s http://<엔진>:8000/metrics | grep -E 'vllm:(num_requests_waiting|kv_cache_usage_perc|gpu_cache_usage_perc)'   # 예: vLLM. 분배기가 점수 매기는 부하 (4단계)
curl -s http://<엔진>:8000/metrics | grep vllm:prefix_cache   # 레플리카별 프리픽스 캐시 조회·적중 (5단계)
```
