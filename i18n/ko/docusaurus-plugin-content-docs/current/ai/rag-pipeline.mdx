# RAG 파이프라인이 문서로 답하기까지

질문 하나를 따라 검색 증강 생성(RAG)을 본다. **문서 → 청크 → 임베딩 → 벡터 DB**, 그리고 **질문 → 같은 임베딩 모델 → 검색 → 리랭킹 → 프롬프트 → LLM**. 답의 품질이 모델에 닿는 청크의 품질을 넘지 못하는 이유를 확인한다.

| 실패 | 증상 | 해결 |
|---|---|---|
| 잘못된 청크 분할 | 사실은 있는데 검색되지 않거나, 표와 목록이 반쯤 잘려 나온다 | 제목, 문단, 표의 행을 따라 자른다. 크기와 겹침을 조정하고 실제 질문으로 시험한다 |
| 오래된 인덱스 | 문서의 옛 버전을 인용한다 | 바뀔 때 재색인한다(이벤트나 자주 도는 CronJob). 문서가 바뀌면 문서 id로 옛 청크를 지운다 |
| 임베딩 모델 불일치 | 업그레이드 뒤 유사도 점수가 엉망이거나 벡터 차원 때문에 질의가 실패한다 | 청크마다 모델 이름을 저장하고, 모델을 바꾸면 인덱스 전체를 다시 만든다 |
| 정확한 단어 놓침 | 코드, 품번, 이름을 묻는 질문에 엉뚱한 청크가 온다 | 키워드 검색(BM25)을 더해 결과를 합친다(하이브리드 검색) |
| 컨텍스트 초과 | 길이 때문에 요청이 거부되거나 뒤쪽 청크를 무시한다 | 토큰을 세고, 리랭킹 뒤 더 적고 좋은 청크만 남기고, 답변 자리를 비워 둔다 |
| 권한 필터 없음 | 열어 볼 수 없는 문서의 내용이 사용자에게 보인다 | 청크마다 허용 그룹을 저장하고 벡터 질의에서 필터한다 |
| 모델이 출처를 무시 | 검색된 청크와 반대로 답하거나 출처를 안 붙인다 | 출처로만 답하고 모자라면 그렇다고 말하라고 지시한다. 충실도를 잰다 |

## 직접 확인해 보기

```bash
# 로컬 PostgreSQL에서 pgvector 써 보기 (pgvector 이미지에 확장이 들어 있다)
docker run -d --name pg -e POSTGRES_PASSWORD=pw -p 5432:5432 pgvector/pgvector:pg17
psql postgresql://postgres:pw@localhost:5432/postgres <<'SQL'
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (id bigserial PRIMARY KEY, doc_id text, groups text[], body text, embedding vector(3));
INSERT INTO chunks (doc_id, groups, body, embedding) VALUES
  ('refund', '{all}',   '개봉 상품: 30일',     '[0.9,0.1,0.0]'),
  ('salary', '{hr}',    '2026 급여 구간',      '[0.1,0.9,0.2]'),
  ('ship',   '{all}',   '배송은 3일 걸린다',    '[0.2,0.1,0.9]');
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);   -- 근사 인덱스
-- <=> 는 코사인 거리(작을수록 가깝다). 사용자 그룹 필터를 같은 질의에 건다.
SELECT doc_id, body, embedding <=> '[0.8,0.2,0.1]' AS distance
FROM chunks WHERE groups && '{all,sales}' ORDER BY distance LIMIT 2;
SQL

# OpenAI 호환 서버에서 임베딩 받기 (많은 모델 서버가 이 엔드포인트를 제공한다)
curl -s http://<임베딩-서버>/v1/embeddings -H 'Content-Type: application/json' \
  -d '{"model":"<임베딩-모델>","input":"반품 기간은 며칠인가?"}' | jq '.data[0].embedding | length'   # 벡터 차원 수
```

실제 임베딩은 수백에서 수천 차원이다. 위의 숫자 세 개짜리 벡터는 질의가 어떻게 돌아가는지만 보여 준다.
