# 시크릿을 안전하게 지키기

쿠버네티스 시크릿은 비밀번호를 이미지 밖으로 빼 줄 뿐, 그것만으로 비밀번호를 지켜 주지는 않는다. DB 비밀번호 하나가 `kubectl apply`로 etcd에 들어가고, 읽는 사람에게 나가고, Git에 실리고, 마지막에 외부 보관소에서 교체되기까지를 따라간다. 시크릿이 환경 변수나 파일로 파드에 들어가는 과정은 [설정과 비밀값](../k8s/config-secret.mdx)에서 먼저 본다.

## 비밀값을 다루는 방식 비교

| 방식 | 값이 있는 곳 | Git에 있는 것 | 교체 |
|---|---|---|---|
| 그냥 시크릿 | etcd(저장 시 암호화가 없으면 평문) | 커밋하면 base64 평문: 피한다 | `kubectl apply`로 직접 |
| Sealed Secrets | 컨트롤러가 푼 뒤 etcd | 암호문(SealedSecret) | 다시 봉인해 새 값 커밋 |
| SOPS | 배포 때 푼 뒤 etcd | 암호화된 값 | 다시 암호화해 커밋 |
| External Secrets Operator | 외부 보관소, 시크릿으로 복사 | 참조만(ExternalSecret) | 보관소에서, `refreshInterval`마다 반영 |
| Secrets Store CSI Driver | 외부 보관소, 파일로 마운트(시크릿은 선택) | 참조만(SecretProviderClass) | 보관소에서, 교체 기능을 켜면 파일 갱신 |
| 동적 자격 증명 | 요청마다 보관소가 발급 | 없음 | 자동, 하나하나가 만료된다 |

## 직접 확인해 보기

```bash
kubectl create secret generic db-pass --from-literal=password=s3cr3t
kubectl get secret db-pass -o jsonpath='{.data.password}' | base64 -d   # base64는 암호화가 아니다

# 실습 클러스터에서만, 컨트롤 플레인 노드에서: etcd 원본 값 읽기
sudo ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  get /registry/secrets/default/db-pass | hexdump -C | head   # s3cr3t가 보이거나, 암호화했다면 k8s:enc:…

kubectl auth can-i list secrets -n default --as=system:serviceaccount:default:default   # "no"여야 한다
kubectl get secrets -A -o json | kubectl replace -f -    # 암호화를 켠 뒤 모든 시크릿 다시 쓰기
kubectl get externalsecret -A                            # STATUS SecretSynced, REFRESH INTERVAL
kubectl get clustersecretstore,secretstore -A            # 오퍼레이터가 보관소에 닿는지
```
