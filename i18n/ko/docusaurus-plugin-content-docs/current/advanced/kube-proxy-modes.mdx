# kube-proxy 모드, 서비스 IP에서 파드 IP로

패킷 레슨에서 서비스 IP는 보내는 노드에서 파드 IP로 바뀐다고 했다. 여기서는 그 상자를 연다. 모드마다 kube-proxy가 커널에 무엇을 써 넣는지, eBPF 데이터패스는 같은 일을 어떻게 하는지, conntrack과 트래픽 정책이 무엇을 바꾸는지 본다.

## 모드 한눈에 비교

| | iptables | IPVS | nftables | eBPF 대체(예: Cilium) |
|---|---|---|---|---|
| 상태 | 지금 기본값 | v1.35부터 지원 중단, 제거 예정 | v1.33부터 GA, 커널 5.13+ | 쿠버네티스 밖, CNI가 제공 |
| 서비스 찾기 | `KUBE-SERVICES` 규칙을 차례로 | 가상 서버 해시 테이블 | verdict 맵 | eBPF 맵 |
| 엔드포인트 선택 | 무작위, `statistic --probability` | 스케줄러: `rr`, `lc`, `sh` 등 | 무작위 | `connect()` 때, 또는 tc/XDP에서 패킷마다 |
| 갱신 | 테이블을 크게 다시 씀 | 가상 서버 단위 | 바뀐 부분만 | 맵 갱신 |
| 볼 곳 | `iptables-save -t nat` | `ipvsadm -Ln` | `nft list table ip kube-proxy` | CNI 도구, 예: `cilium-dbg service list` |

## 직접 확인해 보기

```bash
# 어떤 모드인가? (노드에서; kind 노드는 docker exec -it lab-worker bash)
curl -s localhost:10249/proxyMode                     # kube-proxy 메트릭 포트가 iptables / ipvs / nftables로 답한다
kubectl logs -n kube-system ds/kube-proxy | grep -i proxier   # 예: "Using iptables Proxier"
kubectl get endpointslices -l kubernetes.io/service-name=web  # kube-proxy가 규칙으로 쓰는 엔드포인트

# iptables 모드
iptables-save -t nat | grep -E 'KUBE-SVC|KUBE-SEP' | head     # 체인과 확률 규칙
iptables-save -t nat | grep -c KUBE-SEP                        # 이 노드의 엔드포인트 규칙 수

# nftables·IPVS 모드
nft list table ip kube-proxy | less                   # 맵과 서비스별 체인
ipvsadm -Ln                                           # 가상 서버와 실제 서버

# conntrack
conntrack -L -d 10.96.12.34                           # 이 ClusterIP로 가는 흐름과 DNAT 대상
conntrack -D -p udp --orig-dst 10.96.0.10             # kube-dns로 가는 남은 UDP 항목을 손으로 지우기
```
