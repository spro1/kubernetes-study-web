# 노드 안에서: kubelet, CRI, containerd

스케줄러가 파드를 node-1에 배정했다. 이제부터는 그 노드 안의 일이다. kubelet이 gRPC 소켓으로 컨테이너 런타임에 말을 걸고, 런타임은 runc에게 프로세스를 띄우게 하고, kubelet은 실제로 무엇이 돌고 있는지 계속 확인한다.

## 어느 층을 볼까

| 증상 | 층 | 볼 곳 |
|---|---|---|
| ContainerCreating에 멈춤, 이벤트에 failed to create pod sandbox | 샌드박스 또는 CNI | `kubectl describe pod` 이벤트, CNI 플러그인 파드와 로그, `crictl pods` |
| 샌드박스는 있는데 ContainerCreating에 멈춤 | 이미지 또는 마운트 | `crictl images`, 이미지 받기·볼륨 오류 이벤트 |
| 컨테이너가 뜨자마자 종료 | 앱 또는 설정 | `crictl ps -a`, `crictl logs <id>`, `kubectl logs --previous` |
| 노드 NotReady, kubelet 로그에 PLEG is not healthy | 런타임이 느리거나 멈춤 | `crictl info`, `systemctl status containerd`, `journalctl -u containerd` |
| 노드 NotReady, container runtime is down | 런타임 정지 | `systemctl restart containerd` 후 kubelet 확인 |
| 한 노드에서만 kubectl logs와 exec가 실패 | 그 노드의 kubelet 또는 런타임 | `systemctl status kubelet containerd` |

노드의 프로세스 트리는 containerd → 앱이 아니라 `containerd-shim-runc-v2` → `pause`와 앱 프로세스 모양이다.

## 직접 확인해 보기

```bash
kubectl get pod web -o wide                          # 어느 노드, 어느 IP
kubectl get pod web -o jsonpath='{.status.containerStatuses[0].containerID}{"\n"}'  # containerd://<id>

# 그 노드에서
sudo crictl info | head -40                          # RuntimeReady·NetworkReady 조건
sudo crictl pods --name web                          # 이 파드의 샌드박스(pause)
sudo crictl ps -a --pod <pod-id>                     # 그 샌드박스의 컨테이너, 종료된 것 포함
sudo crictl inspect <container-id> | grep -m1 '"pid"'   # 앱 프로세스의 호스트 PID
sudo crictl logs --tail 20 <container-id>            # kubectl logs가 읽는 바로 그 로그 파일
ps -ef | grep [c]ontainerd-shim                      # 파드마다 심 하나, 프로세스의 부모
sudo journalctl -u kubelet --since -10m | grep -i pleg   # PLEG 상태 메시지
```
