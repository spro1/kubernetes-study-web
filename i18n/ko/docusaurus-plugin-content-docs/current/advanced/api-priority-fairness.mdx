# API 우선순위와 공정성(APF)

버그 난 컨트롤러가 초당 수천 건씩 요청을 보내기 시작한다. 제한이 없으면 kubelet과 리더 선출을 밀어내고 클러스터까지 함께 쓰러뜨린다. API 우선순위와 공정성(APF)은 요청마다 우선순위 수준과 흐름을 정해, 시끄러운 클라이언트는 기다리거나 429를 받고 나머지는 하던 일을 계속하게 한다.

## 관찰한 값이 말해 주는 것

| 관찰 | 뜻 | 다음 할 일 |
|---|---|---|
| 클라이언트가 429를 받고, PriorityLevel UID 헤더가 `workload-low`나 `global-default`에 대응 | 그 흐름이 공정한 몫을 넘었다 | 클라이언트를 고친다(물러서기, 반복 LIST 대신 watch, 페이지 줄이기) |
| `apiserver_flowcontrol_rejected_requests_total`이 `reason="queue-full"`로 증가 | 그 수준의 큐가 가득 찼다 | `dump_requests`에서 상위 흐름을 찾고 클라이언트를 찾는다 |
| 같은 메트릭이 `reason="time-out"` | 요청이 큐에서 너무 오래 기다렸다 | 수준이 실제 수요보다 작거나, 흐름 하나가 독차지한다 |
| `node-high`나 `leader-election`의 `apiserver_flowcontrol_request_wait_duration_seconds`가 높음 | 중요한 트래픽이 기다린다 | 그 수준에 잘못 분류된 것이 있는지 본다 |
| 직접 만든 컨트롤러의 요청이 `catch-all`에 들어감 | 맞는 FlowSchema가 없다 | 알맞은 수준으로 보내는 FlowSchema를 더한다 |
| 중요한 요청이 APF를 건너뛰어야 함 | exempt 수준 | 아껴 쓴다. exempt 트래픽은 무제한이다 |

## 직접 확인해 보기

```bash
kubectl get flowschemas                              # PRIORITYLEVEL, MATCHINGPRECEDENCE, DISTINGUISHERMETHOD
kubectl get prioritylevelconfigurations              # TYPE, NOMINALCONCURRENCYSHARES, QUEUES, HANDSIZE
kubectl get pods -v=8 2>&1 | grep -i x-kubernetes-pf # 내 요청의 FlowSchema와 수준 UID
kubectl get flowschemas -o custom-columns="uid:{metadata.uid},name:{metadata.name}"   # UID를 이름으로
kubectl get --raw /debug/api_priority_and_fairness/dump_priority_levels   # 수준별 좌석과 대기 요청
kubectl get --raw /debug/api_priority_and_fairness/dump_requests          # 지금 누가 기다리는지
kubectl get --raw /metrics | grep apiserver_flowcontrol_rejected_requests_total   # 수준·이유별 거절 수
```
