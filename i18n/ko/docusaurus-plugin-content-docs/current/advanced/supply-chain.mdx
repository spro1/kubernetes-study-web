# 이미지와 공급망 보안

소프트웨어 공급망은 소스 → 의존 패키지 → 빌드 → 이미지 → 배포에 이르는 경로 전체다. 이 중 어디 하나가 오염되면 정상 절차를 그대로 밟아 악성 코드가 배포된다. 이미지 하나가 이 길을 지나는 동안 어디에 어떤 확인 장치가 붙는지 따라가 본다.

## 장치별로 확인하는 것과 한계

| 장치 | 무엇을 확인하나 | 한계 |
| --- | --- | --- |
| 취약점 검사 | 이미지 패키지에 알려진 취약점(CVE)이 있는지 | 알려지지 않은 결함은 못 찾는다. 새 취약점이 공개되면 다시 검사해야 한다 |
| SBOM | 이미지 안의 전체 구성 목록 | 목록일 뿐 안전 증명이 아니다 |
| 서명 | 우리 빌드가 만들었고 중간에 바뀌지 않았는지 | 배포 때 확인하는 정책이 있어야 의미가 있다 |
| 다이제스트 고정 | 정확히 어느 이미지를 배포하는지 | 사람이 읽기 어렵다. 버전 태그를 함께 단다 |

예: Harbor 같은 이미지 저장소는 Trivy를 스캐너로 붙여 저장된 이미지의 취약점 검사를 실행하고, 결과(CVE 식별자·패키지명·설치 버전·수정 버전·심각도)를 보여 준다. 로컬에서는 `trivy image <이미지>`로 같은 검사를 해 볼 수 있다.

## 직접 확인해 보기

```bash
kubectl get pods -n <네임스페이스> -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.containerStatuses[*].imageID}{"\n"}{end}'   # 파드마다 실제로 실행 중인 다이제스트
trivy image --format cyclonedx --output sbom.json <이미지>      # SBOM 만들기
trivy image --severity HIGH,CRITICAL --ignore-unfixed <이미지>   # 수정 버전이 있는 높은 심각도부터
cosign verify --key <공개키> <이미지>                           # 누가 만들었고 바뀌지 않았는지
kubectl get validatingwebhookconfigurations                     # 배포 때 서명을 확인하는 정책이 있는지
```
