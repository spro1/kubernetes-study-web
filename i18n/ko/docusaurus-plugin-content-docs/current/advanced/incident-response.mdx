# 장애 대응: 알람에서 포스트모템까지

## 장애 단계 한눈에 보기

| 단계 | 목표 | 누가 | 흔한 실수 |
|---|---|---|---|
| 감지 | 사용자가 피해를 보는지 안다 | 알람, 당직자 | 증상이 아니라 원인(CPU, 디스크)으로 호출하기 |
| 확인 | 맡은 사람이 생긴다 | 당직자 | 아무도 확인하지 않아 에스컬레이션되는 호출 |
| 선언 | 조율된 대응을 시작한다 | 당직자, 이어서 IC | 너무 늦게 선언하기, 심각도로 논쟁하기 |
| 조율 | 하나의 계획, 하나의 채널 | 장애 지휘자 | IC가 지휘 대신 직접 고치기 |
| 완화 | 사용자 피해를 멈춘다 | 운영 담당, 분야 전문가 | 사용자가 기다리는 동안 근본 원인 디버깅하기 |
| 공지 | 모두가 상황을 안다 | 커뮤니케이션 | 다음 공지 시각이 없어 대응자에게 질문이 몰리기 |
| 해결 | 복구가 유지되는지 확인한다 | IC | 그래프 하나가 좋아지자마자 닫기 |
| 학습 | 재발을 막는다 | 팀 전체 | 사람 탓하기, 담당자 없는 조치 항목 |

흔한 완화 수단과 한계:

| 완화 수단 | 도움이 될 때 | 주의할 점 |
|---|---|---|
| 롤백 | 최근 배포나 설정 변경 | 데이터나 스키마 변경은 되돌리지 않는다 |
| 페일오버 | 리전, 존, 클러스터 하나가 망가졌을 때 | 반대쪽에 용량이 충분해야 한다 |
| 부하 줄이기 | 과부하, 재시도 폭주 | 무엇을 버릴지 정해야 한다(우선순위 낮은 트래픽부터) |
| 기능 플래그 끄기 | 기능 하나가 피해를 낼 때 | 플래그가 미리 있고 시험돼 있어야 한다 |
| 수평 확장 | 실제 수요가 용량을 넘을 때 | 의존 서비스가 병목이면 소용없다 |

```bash
# 최근에 무엇이 바뀌었나? 롤아웃 이력과 최근 이벤트
kubectl rollout history deployment/checkout -n shop
kubectl get events -n shop --sort-by=.lastTimestamp | tail -20

# 완화: 이전 리비전으로 롤백하고 끝날 때까지 기다린다
kubectl rollout undo deployment/checkout -n shop
kubectl rollout status deployment/checkout -n shop

# 나중에 타임라인에서 보이도록 이유를 남긴다
kubectl annotate deployment/checkout -n shop \
  kubernetes.io/change-cause="incident 2026-11-27: roll back v42" --overwrite

# 지금 울리고 있는 알람 (Alertmanager CLI)
amtool --alertmanager.url=http://localhost:9093 alert query
```
