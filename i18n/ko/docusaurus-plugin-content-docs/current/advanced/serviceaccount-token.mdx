# 파드는 자신을 어떻게 증명하나 (서비스 어카운트 토큰)

[RBAC 레슨](../k8s/rbac.mdx)에서는 파드의 요청이 서비스 어카운트 이름으로 검사된다는 것을 봤다. 이 레슨은 그 앞 단계를 확대한다. **파드의 토큰이 어디서 오고, 안에 무엇이 들어 있고, 왜 어느 순간 통하지 않게 되는지** 따라간다.

## 401인가 403인가

| 응답 | 단계 | 흔한 원인 | 확인할 것 |
|---|---|---|---|
| 401 Unauthorized | 인증 | 토큰 만료. 시작할 때 한 번 읽고 다시 읽지 않았다 | 앱이 토큰 파일을 다시 읽는지, 오래된 클라이언트 라이브러리를 올렸는지 |
| 401 Unauthorized | 인증 | 묶인 파드가 지워졌거나 토큰을 다른 곳에 복사해 썼다 | 살아 있는 파드나 `kubectl create token`으로 새 토큰을 받는다 |
| 401 Unauthorized | 인증 | audience가 다르다. 다른 시스템용으로 만든 토큰이다 | `aud` 클레임이 API 서버가 받는 값과 맞는지 |
| 401 Unauthorized | 인증 | 토큰을 아예 보내지 않았다(`automountServiceAccountToken: false`) | 앱이 찾는 위치에 토큰이 마운트됐는지 |
| 403 Forbidden | 인가 | 이 자원에 이 동작을 주는 RoleBinding·ClusterRoleBinding이 없다 | `kubectl auth can-i ... --as=system:serviceaccount:<ns>:<sa>` |
| 403 Forbidden | 인가 | 바인딩은 있지만 다른 네임스페이스에 있다 | RoleBinding의 네임스페이스와 subject의 네임스페이스 |

호환성 때문에 서버 쪽에서 기본 마운트 토큰의 수명을 늘려 두고, 한 시간이 넘은 토큰을 쓰는 앱을 로그로 남기는 클러스터가 많다. 그래도 토큰은 짧게 산다고 생각하고 다룬다.

## 직접 확인해 보기

```bash
kubectl create serviceaccount reporter -n shop
kubectl create token reporter -n shop --duration=10m      # 짧은 토큰을 화면에 출력
kubectl create token reporter -n shop | cut -d. -f2 | base64 -d 2>/dev/null; echo   # 클레임: iss, sub, aud, exp
kubectl auth can-i list configmaps -n shop --as=system:serviceaccount:shop:reporter   # yes / no(= 403)
kubectl exec -n shop <파드> -- ls /var/run/secrets/kubernetes.io/serviceaccount/       # token, ca.crt, namespace
kubectl get pod <파드> -n shop -o jsonpath='{.spec.serviceAccountName}{"\n"}'         # 파드가 쓰는 SA
kubectl get --raw /.well-known/openid-configuration                                   # 발급자와 JWKS 주소
```

JWT 조각은 `=` 패딩을 빼므로 base64 단계에서 짧은 오류가 날 수 있다. 클레임은 그래도 보인다. 파드에 마운트된 토큰의 `kubernetes.io` 클레임에는 묶인 파드가 나온다.
