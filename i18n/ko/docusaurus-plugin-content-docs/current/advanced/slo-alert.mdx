# SLO와 알람 설계

"CPU 80% 초과" 알람이 하루 30번 울리는데 사용자 불만은 없다. 반대로 사용자가 오류를 겪는 동안에는 아무 알람도 없을 수 있다. 사람을 깨우는 알람을 사용자 경험 기준으로 다시 설계하고, 알람이 울린 뒤 원인까지 좁혀 가는 과정을 따라가 본다.

## 원인 기반 알람과 증상 기반 알람

| 구분 | 예 | 결과 | 두는 곳 |
| --- | --- | --- | --- |
| 원인 기반 | CPU 80% 초과, 파드 재시작 1회 | 사용자 영향이 없어도 울려 알람 피로를 부른다 | 대시보드·분석 |
| 증상 기반 | 오류 예산 소진 속도, p99 응답시간 2초 초과 10분 지속 | 사용자가 실제로 겪는 문제일 때만 울린다 | 사람을 깨우는 알람 |

Prometheus를 쓴다면 알람 조건은 알림 규칙(alerting rule)으로 쓰고, 묶기·반복 주기·수신처는 Alertmanager에서 정한다.

## 직접 확인해 보기

```bash
kubectl get --raw /metrics | grep '^apiserver_request_total' | head    # 응답 코드별 요청 수: SLI의 재료
curl -s <프로메테우스>/api/v1/query --data-urlencode 'query=sum(rate(apiserver_request_total{code=~"5.."}[5m])) / sum(rate(apiserver_request_total[5m]))'   # 5분 창의 오류 비율
kubectl get prometheusrules -A                                         # 알람 규칙(Prometheus Operator)
curl -s <프로메테우스>/api/v1/rules | jq '.data.groups[].rules[].name'   # 프로메테우스가 실제로 읽은 규칙
curl -s <얼럿매니저>/api/v2/alerts/groups                              # 한 통으로 묶인 알림
```
