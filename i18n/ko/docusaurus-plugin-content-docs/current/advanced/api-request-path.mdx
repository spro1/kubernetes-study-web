# API 요청이 저장되기까지

대시보드의 `[생성]` 버튼이나 `kubectl apply`가 보낸 요청은 API 서버 안에서 여러 관문을 거친 뒤에야 저장된다. **어느 관문에서 거절되느냐에 따라 사용자가 보는 오류가 다르다.** 인증·인가는 [누가 무엇을 할 수 있나 (RBAC)](../k8s/rbac.mdx)에서, 저장 뒤 파드가 뜨는 과정은 [파드가 뜨기까지](../k8s/pod-startup.mdx)에서 다뤘으니, 여기서는 그 사이의 어드미션과 저장, 충돌에 집중한다.

## 관문별로 보이는 오류

| 관문 | 거절되면 | 사용자에게 보이는 것 |
| --- | --- | --- |
| 인증 | `401 Unauthorized` | 로그인이 풀렸거나 접속 정보가 만료됨 |
| 인가 (RBAC) | `403 Forbidden` | 권한 없음. 메시지에 사용자·동사·자원이 적혀 있다 |
| 변경 어드미션 | 드물게 거절 | 저장된 YAML이 입력한 것과 다르게 보인다 |
| 스키마 검증 | `422 Unprocessable Entity` | "필드가 올바르지 않다"는 오류 |
| 검증 어드미션 | `403` 또는 정책별 메시지 | "쿼터를 초과했다", `admission webhook "..." denied the request` |
| 웹훅 서버 무응답 | `failed calling webhook` | 시간 초과. 그 웹훅이 걸린 범위의 생성이 전부 실패할 수 있다 |
| 저장 | `409 Conflict` | 같은 이름이 이미 있거나, 다른 주체가 먼저 고쳤다 |

## 직접 확인해 보기

```bash
kubectl get pods -n kube-system -v=6                                    # 요청 하나가 HTTP 한 번: 메서드·URL·응답 코드
kubectl auth can-i create deployments -n <네임스페이스>                 # 인가를 통과하는지, 403인지
kubectl get mutatingwebhookconfigurations,validatingwebhookconfigurations -o custom-columns=NAME:.metadata.name,FAILURE:.webhooks[*].failurePolicy   # 길목의 웹훅과 failurePolicy
kubectl create deployment demo --image=nginx --dry-run=server -o yaml   # 관문은 다 거치되 저장은 안 한다. 붙은 필드를 본다
kubectl get deployment <이름> -o jsonpath='{.metadata.resourceVersion}'   # 저장될 때마다 바뀐다
```
