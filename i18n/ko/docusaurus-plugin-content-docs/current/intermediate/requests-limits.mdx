# 요청값과 상한값

컨테이너마다 자원을 "최소한 이만큼 필요하다(요청값)"와 "이 이상은 못 쓴다(상한값)" 두 값으로 적는다. 두 값이 배치할 때와 실행 중에 각각 어떻게 쓰이는지 따라가 본다. 스케줄러가 노드를 거르고 고르는 자세한 과정은 [파드를 어느 노드에 둘까 (스케줄링)](../k8s/scheduling.mdx)에서 다룬다.

## 오해와 사실

| 오해 | 사실 |
| --- | --- |
| 사용률이 낮으면 파드가 들어갈 자리가 있다 | 스케줄러는 요청값 합계만 본다. 할당률이 차면 사용률과 무관하게 `Pending`이다 |
| 상한을 넘으면 CPU든 메모리든 종료된다 | CPU는 느려질 뿐(스로틀링)이고, 메모리만 강제 종료(`OOMKilled`)된다 |
| 요청값은 비워 둬도 된다 | 배치 판단이 틀어지고, 쿼터가 있는 구획에서는 생성이 거절되며, HPA가 사용률을 계산하지 못한다 |
| HPA CPU 80%는 상한값의 80%다 | 요청값 기준이다 |
| 요청값은 넉넉할수록 안전하다 | 자리가 있는데도 배치되지 않고 자원이 낭비된다 |

## 직접 확인해 보기

```bash
kubectl get pod <파드> -o jsonpath='{.spec.containers[*].resources}'   # requests와 limits
kubectl get pod <파드> -o jsonpath='{.status.qosClass}'   # QoS 클래스(축출 순서)
kubectl top pod                                      # 실제 사용량(metrics-server 필요)
kubectl describe node <노드> | grep -A 8 'Allocated resources'   # 노드의 requests 합계
kubectl get pod <파드> -o jsonpath='{.status.containerStatuses[*].lastState.terminated.reason}'   # OOMKilled인지
```
