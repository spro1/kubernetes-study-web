# 4C와 위협 모델로 클러스터 보기 (KCSA·KCNA)

## 시험에서 자주 묻는 것

| 상황 | 해야 할 일·명령 | 함정 |
| --- | --- | --- |
| 4C 순서를 묻는다 | 바깥부터 Cloud → Cluster → Container → Code | 안쪽 층은 바깥 층의 보안에 기댄다. 코드만 지켜서는 부족하다 |
| 침해된 파드가 다른 파드에 닿는다 | 네임스페이스에 기본 차단 NetworkPolicy, 필요한 통신만 허용 | 기본 상태는 모든 파드끼리 통신이 열려 있다 |
| 파드 토큰으로 권한 상승 | 서비스 어카운트 최소 권한, `automountServiceAccountToken: false` | 파드 생성 권한도 다른 계정 권한을 빌리는 경로가 된다 |
| 시크릿 보호 | etcd 저장 암호화(`EncryptionConfiguration`) + 시크릿 조회 RBAC 축소 | base64는 암호화가 아니다 |
| 서비스 거부 | requests·limits, ResourceQuota, API 우선순위와 공정성 | limits가 없으면 한 파드가 노드의 이웃 파드까지 굶긴다 |
| 지속성·침해 경로 추적 | 감사 로그에서 create·exec 요청과 사용자를 확인 | 감사 로그는 감사 정책을 설정해야 남는다 |

경계별 방어를 하나씩 깊게 보려면 [통신 막고 열기 (네트워크 정책)](../k8s/network-policy.mdx), [누가 무엇을 할 수 있나 (RBAC)](../k8s/rbac.mdx), [파드 보안 기준과 securityContext](../advanced/pod-security.mdx), [감사 로그](../advanced/audit-log.mdx) 레슨을 이어서 본다.

## 직접 확인해 보기

```bash
kubectl get networkpolicy -A                         # 네임스페이스마다 기본 거부가 있는지
kubectl get ns -L pod-security.kubernetes.io/enforce   # 네임스페이스별 Pod Security Standard
kubectl auth can-i --list --as=system:serviceaccount:<네임스페이스>:<서비스어카운트>   # 파드 토큰으로 할 수 있는 일
kubectl get resourcequota -A                         # 서비스 거부를 막는 쿼터
sudo grep -E 'encryption-provider-config|audit-policy-file' /etc/kubernetes/manifests/kube-apiserver.yaml   # Secret 암호화와 감사가 켜졌는지(kubeadm)
```
