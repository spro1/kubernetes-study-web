# 런타임 보안 — 이상 행동 잡기 (CKS)

CKS 출제 영역 중 Monitoring, Logging and Runtime Security(20%)와 System Hardening(10%)의 "AppArmor·seccomp 같은 커널 강화 도구"에 해당한다. 배포 전 검사를 모두 통과한 컨테이너라도 실행 중(런타임)에 뚫릴 수 있다. 실행 중인 컨테이너 안에서 일어나는 이상 행동을 어떻게 알아채고, 막고, 조사하는지 따라가 본다. 파드를 만들 때 거는 보안 기준은 [파드 보안 기준과 securityContext](../advanced/pod-security.mdx)에서, 감사 로그 정책은 [감사 로그](../advanced/audit-log.mdx)에서 먼저 본다.

## 시험에서 자주 묻는 것

| 상황 | 해야 할 일·명령 | 함정 |
| --- | --- | --- |
| 셸을 연 컨테이너 찾기 | Falco 출력에서 규칙 이름과 컨테이너·파드 이름을 확인하고 해당 파드를 교체 | Falco는 알리기만 한다. 파드는 직접 정리해야 한다 |
| Falco 규칙 추가·수정 | 기본 규칙 파일 대신 `falco_rules.local.yaml` 같은 로컬 규칙 파일에 적는다 | 기본 규칙 파일을 고치면 업그레이드 때 덮어써질 수 있다 |
| 컨테이너 불변성 | `readOnlyRootFilesystem: true`, 쓰기가 필요한 경로만 `emptyDir` | 임시 파일을 쓰는 앱은 볼륨 없이 시작에 실패한다 |
| seccomp 적용 | `securityContext.seccompProfile.type: RuntimeDefault` 또는 `Localhost` | `Localhost` 프로파일 경로는 kubelet의 seccomp 폴더 기준이다 |
| AppArmor 적용 | 노드에서 `apparmor_parser`로 프로파일을 올리고 `appArmorProfile`에 이름 지정 | 프로파일이 없는 노드에 배치되면 파드가 시작되지 못한다 |
| 누가 exec 했나 | 감사 로그에서 `pods/exec` 요청의 사용자 확인 | 감사 정책에 규칙이 없으면 남지 않는다 |

## 직접 확인해 보기

```bash
kubectl logs -n falco -l app.kubernetes.io/name=falco -c falco   # Falco 경보(Helm 설치 기준)
kubectl get pod <파드> -o jsonpath='{.spec.securityContext}'   # 파드 수준 seccomp/AppArmor
kubectl get pod <파드> -o jsonpath='{.spec.containers[*].securityContext}'   # readOnlyRootFilesystem 등
sudo aa-status | grep deny-shell                     # 노드에서: 프로파일이 올라왔는지
sudo grep '"subresource":"exec"' /var/log/kubernetes/audit/audit.log   # 누가 exec했는지(경로는 --audit-log-path)
```
