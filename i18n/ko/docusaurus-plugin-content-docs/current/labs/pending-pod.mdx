# 실습 01 · 배치되지 않는 파드

이 실습은 [노트북에 실습 클러스터 만들기](../basic/lab-cluster.mdx)에서 만든 노드 3개짜리 kind 클러스터(control-plane 1개, worker 2개)에서 한다. 먼저 `kubectl config current-context`가 `kind-lab`인지 확인한다.

## 목표

디플로이먼트를 적용했는데 파드가 시작되지 않는다. 스케줄러가 왜 파드를 배치하지 못하는지 찾고, 파드가 실행되도록 디플로이먼트를 고친다.

## 준비

```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: lab-01
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: lab-01
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      nodeSelector:
        disktype: ssd
      containers:
        - name: nginx
          image: nginx:1.27
          resources:
            requests:
              cpu: "100"
              memory: 64Mi
EOF
```

## 증상

```bash
kubectl -n lab-01 get pods
```

```text
NAME                   READY   STATUS    RESTARTS   AGE
web-7c9d8f6b5d-q2x8m   0/1     Pending   0          45s
```

파드 이름 끝부분은 다를 수 있다. 아무리 기다려도 파드는 `Pending`이고, `kubectl logs`로는 아무것도 볼 수 없다.

## 살펴보기

```bash
kubectl -n lab-01 get pods -o wide          # 어느 노드인가? NODE 칸을 본다
kubectl -n lab-01 describe pod -l app=web   # 맨 아래 Events를 읽는다
kubectl get nodes --show-labels              # 노드에 실제로 붙은 레이블은?
kubectl get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu,MEMORY:.status.allocatable.memory
```

파드가 요구하는 것과 노드가 내줄 수 있는 것을 비교한다. 아직 실행된 컨테이너가 없으니 스케줄러가 남긴 이유는 로그가 아니라 파드 이벤트에 있다.

## 힌트

<details>
<summary>힌트 1</summary>

NODE 칸이 `<none>`이다. 스케줄러가 노드를 고르지 못했다는 뜻이니 `FailedScheduling` 이벤트를 찾는다. 이 이벤트는 노드 수를 세고 노드 묶음마다 이유를 하나씩 적는다.

</details>

<details>
<summary>힌트 2</summary>

control-plane 노드에는 일반 파드가 견디지 못하는 테인트가 있다. kind에서는 메시지의 이 부분이 정상이다. worker 두 개에 적힌 이유를 보고, 파드의 `nodeSelector`를 `kubectl get nodes --show-labels` 결과와 비교한다.

</details>

<details>
<summary>힌트 3</summary>

문제는 두 개다. 스케줄러는 노드가 처음 걸린 필터에서 멈추기 때문에 이벤트에는 하나만 보일 수 있다. 첫 번째를 고친 뒤 새 이벤트에서 두 번째를 읽는다. `resources.requests.cpu`를 본다. `"100"`은 CPU 100개를 뜻한다.

</details>

## 정답

<details>
<summary>정답</summary>

**문제 1: 어느 노드에도 없는 레이블.** 이벤트는 다음과 같다(버전에 따라 문구가 조금 다르고, 뒤에 `preemption:` 설명이 붙는다).

```text
Warning  FailedScheduling  ...  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node(s) didn't match Pod's node affinity/selector.
```

파드의 `nodeSelector`가 `disktype=ssd`를 요구하는데 이 레이블이 붙은 노드가 없다. 스케줄러는 `nodeSelector`의 모든 키와 레이블이 맞는 노드에만 파드를 둔다. 셀렉터를 지운다.

```bash
kubectl -n lab-01 patch deployment web --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/nodeSelector"}]'
```

(파드가 정말 SSD 노드가 필요하다면 대신 맞는 노드에 레이블을 붙인다. `kubectl label node lab-worker disktype=ssd`. 실습이 끝나면 `kubectl label node lab-worker disktype-`로 지운다.)

**문제 2: 어느 노드보다 큰 요청값.** 새 파드도 여전히 Pending이고, 이벤트에 적힌 worker의 이유가 바뀐다.

```text
Warning  FailedScheduling  ...  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient cpu.
```

`cpu: "100"`은 CPU 코어 100개를 요청한다. 스케줄러는 요청값을 노드의 할당 가능한 CPU에서 다른 파드가 이미 요청한 양을 뺀 값과 비교하는데, 코어가 100개인 kind 노드는 없다. 현실적인 값으로 바꾼다.

```bash
kubectl -n lab-01 set resources deployment web --requests=cpu=100m,memory=64Mi
```

`100m`은 CPU 0.1개다. 파드 템플릿을 바꿀 때마다 새 레플리카셋이 생기고, 새 파드가 실행되면 디플로이먼트가 Pending인 옛 파드를 지운다.

</details>

## 확인

```bash
kubectl -n lab-01 rollout status deployment web
kubectl -n lab-01 get pods -o wide
```

```text
deployment "web" successfully rolled out
NAME                   READY   STATUS    RESTARTS   AGE   IP           NODE          ...
web-5b6f9c7d4f-8mhtk   1/1     Running   0          20s   10.244.1.7   lab-worker    ...
```

파드가 `Running`이고 `1/1` 준비됐으며, NODE 칸에 worker 이름이 있다.

## 정리

```bash
kubectl delete ns lab-01
```
