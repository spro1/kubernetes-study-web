# 관리형 쿠버네티스 — 누가 무엇을 운영하나

관리형 쿠버네티스(예: Amazon EKS, Google GKE, Azure AKS)에서는 클라우드 사업자가 컨트롤 플레인을 운영하고, 워커 노드는 내가 운영한다. 한 팀이 `kubectl`에 로그인해 앱을 띄우고, 외부에 열고, 자동으로 늘리기까지 따라가며 쿠버네티스가 어디서 클라우드에 일을 넘기는지 본다.

## 누가 무엇을 관리하나

| 부분 | 사업자 | 나 |
|---|---|---|
| API 서버, etcd, 스케줄러, 컨트롤러 매니저 | 운영, 패치, 백업, 확장 | 버전과 등급 선택, 컨트롤 플레인 로그 켜기 |
| 컨트롤 플레인 버전 | 버전 출시, 지원 종료 시 강제 업그레이드 가능 | 업그레이드 시작, 폐기 예정 API 확인 |
| 워커 노드 | 노드 이미지와 관리형 노드 그룹·풀 제공 | 크기, 개수, OS 이미지, 업그레이드 시점 (Auto Mode·Autopilot에서는 줄어듦) |
| 네트워크 | CNI와 클라우드 LB 연동 제공 | VPC, 서브넷, IP 대역, 보안 그룹, NetworkPolicy |
| 접근 | 클라우드 신원 확인 | 신원을 RBAC에 연결, 최소 권한 부여 |
| 워크로드, Secret, 데이터 | — | 전부: 매니페스트, 볼륨 백업, 앱 보안 |

사업자마다 이름이 다르다.

| 개념 | EKS | GKE | AKS |
|---|---|---|---|
| 워커 VM 묶음 | 관리형 노드 그룹 | 노드 풀 | 노드 풀 |
| kubectl 로그인 도우미 | `aws eks get-token` | `gke-gcloud-auth-plugin` | `kubelogin` |
| 클라우드 신원 → RBAC | 액세스 항목 (access entry) | IAM + RBAC | Microsoft Entra ID + RBAC |
| 파드 → 클라우드 역할 | IRSA, EKS Pod Identity | Workload Identity Federation for GKE | Microsoft Entra Workload ID |
| 노드까지 사업자가 운영 | EKS Auto Mode | Autopilot | AKS Automatic |

```bash
aws eks update-kubeconfig --name demo --region ap-northeast-2   # 토큰 도우미가 든 kubeconfig 작성 (EKS 예시)
kubectl config view --minify                         # 비밀번호 대신 exec 플러그인이 보인다
kubectl auth whoami                                  # 내 클라우드 신원이 연결된 쿠버네티스 사용자
kubectl get nodes -L topology.kubernetes.io/zone,node.kubernetes.io/instance-type   # 노드는 영역에 있는 VM이다
kubectl get svc -A --field-selector spec.type=LoadBalancer   # 클라우드 LB를 만든 Service
kubectl get pv -o custom-columns=NAME:.metadata.name,ZONE:.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values   # 디스크마다 어느 영역인지
kubectl get events -A --field-selector reason=FailedScheduling   # 오토스케일러가 봐야 할 Pending 파드
kubectl version                                      # 클라이언트와 컨트롤 플레인 버전
```
