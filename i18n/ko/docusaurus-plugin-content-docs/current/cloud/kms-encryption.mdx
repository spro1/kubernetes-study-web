# 클라우드 KMS가 데이터를 암호화하는 방식 (봉투 암호화)

앱이 고객 파일을 암호화해서 저장해야 한다. 키를 코드나 설정에 둘 수는 없다. 클라우드 KMS(여기서는 AWS KMS, Google Cloud KMS와 Azure Key Vault도 비슷하다)가 키를 어떻게 지키는지, 그리고 키를 KMS 밖으로 꺼내지 않고 **봉투 암호화**로 데이터를 어떻게 암호화하는지 따라간다.

## KMS 호출이 실패할 때

| 오류 (AWS KMS) | 흔한 원인 | 해결 |
|---|---|---|
| AccessDeniedException | 키 정책이 호출자나 그 계정을 허용하지 않거나, IAM 정책에 그 동작이 없다 | 키 정책부터 읽고 호출자의 IAM 정책을 본다. 다른 계정이면 양쪽 다 필요하다 |
| DisabledException | 키가 비활성화되어 있다 | 다시 활성화하거나 앱이 맞는 키를 쓰게 한다 |
| KMSInvalidStateException | 키가 삭제 대기(또는 가져오기 대기) 중이다 | 실수라면 `cancel-key-deletion` 뒤 키를 활성화한다 |
| InvalidCiphertextException | 암호문이 틀렸거나 손상됐고, 또는 암호화 컨텍스트가 암호화 때와 다르다 | Decrypt에 똑같은 암호화 컨텍스트를 넘긴다 |
| ThrottlingException | 그 리전에서 계정이 공유하는 초당 요청 한도를 넘었다 | 백오프로 재시도하고, 데이터 키를 재사용하고, 버킷 키를 쓰거나 한도 증가를 요청한다 |
| NotFoundException | 키 ID, 별칭, 리전이 틀렸다 | 특히 다른 계정에서는 전체 키 ARN을 쓴다 |

다른 클라우드도 생각은 같다. Google Cloud KMS는 교체를 "키 버전"으로 다루고, Azure Key Vault는 삭제 대기 기간 대신 보존 기간이 있는 소프트 삭제를 쓴다.

## 직접 확인해 보기

```bash
aws kms create-key --description "app data"                    # KeyId를 돌려준다
aws kms create-alias --alias-name alias/app-data --target-key-id <key-id>
aws kms generate-data-key --key-id alias/app-data --key-spec AES_256 \
  --query CiphertextBlob --output text | base64 --decode > datakey.enc   # 암호화한 사본만 남긴다
aws kms decrypt --ciphertext-blob fileb://datakey.enc \
  --query KeyId --output text                                   # 암호문에서 KMS가 키를 찾아낸다
aws kms get-key-policy --key-id alias/app-data --policy-name default --output text   # 누가 이 키를 쓸 수 있나
aws kms enable-key-rotation --key-id <key-id>                   # --rotation-period-in-days 없으면 365일
aws kms get-key-rotation-status --key-id <key-id>
aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=Decrypt --max-results 5   # 누가 썼나
aws kms schedule-key-deletion --key-id <key-id> --pending-window-in-days 7   # 시험용 키에서만
aws kms cancel-key-deletion --key-id <key-id>                   # 대기 기간 안이면 되돌린다
```
