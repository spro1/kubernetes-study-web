# 사람을 위한 싱글 사인온 (SSO와 페더레이션)

엔지니어 한 명이 클라우드 콘솔, 쿠버네티스 클러스터, 사내 앱 몇 개를 써야 한다. **ID 제공자**(IdP) 하나가 그 사람의 계정이 있는 유일한 곳이 되고, 다른 시스템은 사용자를 따로 두지 않고 그 IdP를 믿게 되는 과정을 따라간다. OIDC 로그인 한 번이 어떻게 도는지는 [로그인은 이렇게 동작한다 (세션, JWT, OIDC)](../basic/auth-login.mdx)에서, 클라우드 API가 요청 권한을 검사하는 방식은 [API 요청 하나의 권한 검사 (IAM)](../cloud/iam-request.mdx)에서 다룬다.

## SAML이냐 OIDC냐

| | SAML 2.0 | OpenID Connect |
|---|---|---|
| 바탕 | XML, 서명된 어서션 | OAuth 2.0, 서명된 JWT(ID 토큰) |
| 전달 방식 | 브라우저가 어서션을 서비스로 POST한다 | 코드를 들고 리다이렉트하고, 클라이언트가 토큰을 받아 온다 |
| 주로 쓰는 곳 | 클라우드 콘솔, 기업용 SaaS | 웹·모바일 앱, CLI, kubectl |
| 브라우저 없이 | 어렵다 | 된다. 디바이스 플로나 로컬 리다이렉트를 쓴다 |
| 로그인 전 사용자 미리 만들기 | 하지 않는다. SCIM을 쓴다 | 하지 않는다. SCIM을 쓴다 |

누군가 떠날 때는 IdP에서 비활성화하고(모든 곳의 새 로그인이 막힌다), SCIM이 아래 시스템에서도 비활성화했는지 확인하고, 민감한 시스템의 세션을 끊고, IAM 사용자, 로컬 계정, 개인 액세스 토큰처럼 SSO 밖에 있는 것을 찾는다.

## 직접 확인해 보기

```bash
aws configure sso                                  # 프로필 설정: 시작 URL, 계정, 권한 세트
aws sso login --profile dev                        # 브라우저를 열어 IdP에서 로그인
aws sts get-caller-identity --profile dev          # ARN에 assumed-role/AWSReservedSSO_... 가 보인다
aws sso-admin list-instances                       # Identity Center 인스턴스와 ID 저장소 ID
aws sso-admin list-permission-sets --instance-arn <instance-arn>
aws identitystore list-groups --identity-store-id <store-id>   # SCIM으로 IdP에서 넘어온 그룹
aws iam generate-credential-report && aws iam get-credential-report \
  --query Content --output text | base64 --decode | cut -d, -f1,4,9,10   # 남아 있는 IAM 사용자와 살아 있는 키
kubectl oidc-login setup --oidc-issuer-url=https://login.example.com --oidc-client-id=kubernetes   # kubelogin 플러그인
kubectl auth whoami                                # 토큰에서 읽은 사용자 이름과 그룹
```
