# 네트워크 잇기: 피어링·트랜짓·VPN·프라이빗 엔드포인트

한 회사에 사무실 네트워크와 VPC 두 개가 있다. 나중에 파트너 서비스를 쓰고, 다른 회사도 인수한다. 각 네트워크는 사설망이라 기본으로 서로 끊겨 있다. 어떤 연결이 무엇을 잇는지, 왜 트래픽에는 양방향 경로가 있어야 하는지, 왜 IP 대역을 일찍 계획해야 하는지 따라가 본다. VPC 하나 안에서 일어나는 일은 [VPC 안에서 요청이 가는 길](../cloud/vpc-request.mdx)에서 먼저 볼 수 있다.

## 네트워크를 잇는 방법

| 방법 | 쓰는 때 | 전이되는가 | 대역폭 | 비용 구조 |
|---|---|---|---|---|
| VPC 피어링 | VPC 두 개가 직접 통해야 할 때 | 아니오 | 가운데 게이트웨이가 없어 한 곳에 몰리지 않음 | 시간당 요금 없음, 데이터 전송 요금 |
| 트랜짓 게이트웨이(허브) | VPC와 온프레미스 거점이 많을 때 | 예, 라우팅 테이블을 따라 | 높음, 연결마다 한도 있음 | 연결 시간당 + 처리한 GB당 |
| 사이트 간 VPN | 인터넷을 지나는 암호화 연결이 빨리 필요할 때 | 허브를 거치면 | AWS 기준 터널당 약 1.25Gbps(대역폭 큰 터널은 5Gbps), 지연은 인터넷 따라 | 연결 시간당 + 나가는 데이터 |
| 전용선 | 사무실·데이터센터 트래픽이 많고 일정할 때 | 게이트웨이나 허브를 거치면 | 1Gbps~100Gbps 이상, 지연 일정 | 포트 시간당 + 나가는 데이터, 개통에 몇 주 |
| 프라이빗 엔드포인트 | 네트워크 전체가 아니라 서비스 하나만 쓸 때 | 아니오, 서비스 하나로 한 방향 | 엔드포인트마다 | 영역별 엔드포인트 시간당 + GB당 |

## 사업자별 이름

| 개념 | AWS | Azure | Google Cloud |
|---|---|---|---|
| 피어링 | VPC peering | VNet peering | VPC Network Peering |
| 허브 | Transit Gateway | Virtual WAN 또는 허브 VNet | Network Connectivity Center |
| VPN | Site-to-Site VPN | VPN Gateway | Cloud VPN (HA VPN) |
| 전용선 | Direct Connect | ExpressRoute | Cloud Interconnect |
| 프라이빗 엔드포인트 | PrivateLink | Private Link (프라이빗 엔드포인트) | Private Service Connect |
| 하이브리드 DNS | Route 53 Resolver 엔드포인트 | DNS Private Resolver | Cloud DNS 전달 영역·인바운드 정책 |

```bash
aws ec2 describe-vpc-peering-connections --query 'VpcPeeringConnections[].[VpcPeeringConnectionId,Status.Code,RequesterVpcInfo.CidrBlock,AccepterVpcInfo.CidrBlock]'
aws ec2 describe-transit-gateway-attachments --query 'TransitGatewayAttachments[].[ResourceType,ResourceId,State]'
aws ec2 describe-vpn-connections --query 'VpnConnections[].VgwTelemetry[].[OutsideIpAddress,Status,AcceptedRouteCount]'

# 사무실 서버에서
traceroute 10.2.3.20          # 길이 어디서 끊기는가
dig db.data.internal          # 이름이 연결 너머로 풀리는가
nc -vz 10.2.3.20 5432         # 거부(닿았지만 듣는 프로세스 없음)인가, 타임아웃(버려짐)인가
```
