# 앱이 데이터베이스에 저장할 때

주문 앱이 주문 하나를 관계형 데이터베이스에 저장한다. 예시는 PostgreSQL이지만 MySQL 같은 다른 관계형 DB도 비슷하게 움직인다. 앱의 **커넥션 풀**에서 **쿼리 플래너**를 거쳐 **트랜잭션**과 **WAL(write-ahead log, 선행 기록 로그)**, 그리고 **읽기 복제본**까지 주문을 따라가 본다.

## 자주 만나는 DB 문제

| 증상 | 흔한 원인 | 확인할 것 |
|---|---|---|
| `sorry, too many clients already` | 모든 앱 레플리카의 연결 합이 `max_connections`를 넘음 | `SELECT count(*) FROM pg_stat_activity;`, 풀 크기 × 레플리카 수, 앞단에 PgBouncer 같은 풀러 두기 |
| 한 화면만 느리고 DB CPU가 높음 | 큰 테이블의 Seq Scan, 인덱스 없음 | `EXPLAIN ANALYZE <쿼리>`, 가장 느린 쿼리는 `pg_stat_statements` |
| 요청이 멈췄다가 타임아웃 | 긴 트랜잭션이 행 잠금을 붙잡고 있음 | `pg_stat_activity`에서 `wait_event_type = 'Lock'`, `pg_blocking_pids(pid)` |
| `deadlock detected` | 두 트랜잭션이 같은 행들을 다른 순서로 잠금 | 서버 로그의 두 문장 확인, 행을 한 순서로 잠그고 앱에서 재시도 |
| 저장은 됐는데 안 보임 | 뒤처진 복제본에서 읽음 | `pg_stat_replication`의 `replay_lag`, 방금 쓴 것은 주 서버에서 읽기 |
| 모든 쓰기에서 COMMIT이 느림 | WAL 디스크 flush가 느림 | WAL 볼륨의 디스크 지연, `pg_stat_io`의 WAL 쓰기·fsync 시간(PostgreSQL 18+) 또는 `pg_stat_wal`(17 이하) |


```sql
CREATE TABLE orders (id bigserial PRIMARY KEY, customer_id int, status text, created_at timestamptz DEFAULT now());
INSERT INTO orders (customer_id, status)
  SELECT (random()*10000)::int, 'paid' FROM generate_series(1, 1000000);
ANALYZE orders;
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;   -- Seq Scan
CREATE INDEX ON orders (customer_id);
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;   -- Index 또는 Bitmap 스캔, 훨씬 빠름
SHOW max_connections;
SELECT pid, state, wait_event_type, query FROM pg_stat_activity;          -- 누가 연결했고 누가 기다리는지
SELECT client_addr, state, replay_lag FROM pg_stat_replication;           -- 복제본이 있는 주 서버에서
```
