# 파이프라인이 도는 순서

CI/CD는 코드 변경이 서비스에 반영되기까지의 빌드 → 테스트 → 배포 과정을 미리 정해 두고 자동으로 실행하는 방식이다. 특정 제품이 아닌 일반적인 파이프라인 하나가 처음부터 끝까지 도는 순서를 따라가 본다. 쿠버네티스에서 Git을 기준으로 배포를 맞추는 방식은 [Helm과 GitOps](../intermediate/gitops-sync.mdx)에서 다룬다.

## 쿠버네티스에서 흔히 쓰는 방식

| 개념 | 일반적인 파이프라인 | 쿠버네티스 환경에서 |
| --- | --- | --- |
| 트리거 | 수동·코드 변경·예약·외부 호출 | 저장소 웹훅으로 CI가 돌고, GitOps 도구가 Git 변경을 감시해 클러스터를 맞춘다(예: Argo CD) |
| 단계와 작업 | 단계는 순서대로, 같은 단계 작업은 동시에 | 작업 하나가 실패했을 때 나머지를 멈출지는 도구 설정에 따라 다르다 |
| 아티팩트 | 이미지를 태그와 함께 레지스트리에 보관 | 이미지를 레지스트리(예: Harbor)에 올리고, 매니페스트에는 그 태그나 다이제스트를 적는다 |
| 운영 반영 승인 | 승인 절차를 두는 곳이 많다 | 수동 승인 단계나 머지 리퀘스트 승인을 관문으로 둔다 |
| 롤백 | 이전 배포 기록이 있어야 되돌릴 수 있다 | `kubectl rollout undo`로 이전 리비전으로 되돌리거나, GitOps라면 Git 커밋을 되돌린다 |

## 직접 확인해 보기

```bash
git log -1 --format='%H %s'                          # 파이프라인이 빌드한 커밋
docker image inspect <이미지> --format '{{.RepoDigests}}'   # 저장된 산출물의 다이제스트
kubectl get deploy <이름> -n <네임스페이스> -o jsonpath='{.spec.template.spec.containers[*].image}{"\n"}'   # dev, stg, prod가 같은 이미지인지
kubectl rollout history deploy/<이름> -n <네임스페이스>   # 배포 이력
kubectl rollout status deploy/<이름> -n <네임스페이스>   # 배포가 끝났는지
```
