# 분산 시스템 기초

한 컴퓨터 안에서 함수 호출은 값을 돌려주거나 예외를 던진다. 네트워크를 건너면 세 번째 답이 있다. 침묵이다. 주문 하나를 **클라이언트 → 주문 서비스 → 데이터베이스와 복제본 → 아웃박스 → 큐 → 배송** 순서로 따라가며, 모든 클라우드 시스템이 겪는 문제와 그것을 다루는 단순한 패턴을 만난다.

## 문제 → 패턴

| 만나는 문제 | 일어나는 이유 | 패턴 |
|---|---|---|
| 타임아웃, 쓰기가 됐는지 모름 | 사라진 답, 느린 노드, 부분 장애 | 멱등 키, 백오프를 둔 안전한 재시도 |
| 메시지 중복 | 최소 한 번 전달, 장애 뒤 재시도 | 이벤트 id, 멱등한 컨슈머 |
| 방금 쓴 데이터가 안 읽힘 | 비동기 복제 지연 | 자기 쓰기 읽기: 프라이머리에서 읽거나 복제본이 따라올 때까지 기다림 |
| 갈라진 양쪽이 모두 쓰기를 받음 | 과반수 규칙이 없음 | 쿼럼 기반 합의(etcd의 Raft), 홀수 구성원 |
| 더 새로운 업데이트가 사라짐 | 벽시계 시각으로 순서를 정함 | 버전 번호, 낙관적 동시성 제어(409 Conflict) |
| 주문은 저장됐는데 이벤트가 안 나감 | DB와 브로커에 이중 쓰기 | 트랜잭셔널 아웃박스와 릴레이 |

| 모델 | 읽기가 돌려줄 수 있는 것 | 흔한 쓰임 |
|---|---|---|
| 강한 일관성(선형화 가능) | 마지막으로 끝난 쓰기만 | 리더 선출, 락, 잔액 |
| 자기 쓰기 읽기 | 내 쓰기는 반드시, 남의 쓰기는 나중일 수도 | 사용자 프로필, "내 주문" |
| 최종 일관성 | 한동안 옛 데이터, 결국 같아짐 | 캐시, 검색 인덱스, 피드 |

```bash
# 쿠버네티스의 낙관적 동시성: 옛 resourceVersion을 바탕으로 한 업데이트는 실패한다
kubectl create configmap demo --from-literal=count=1
kubectl get configmap demo -o yaml > old.yaml                      # 지금의 resourceVersion을 기억해 둔다
kubectl patch configmap demo -p '{"data":{"count":"2"}}'            # 누군가 그사이 바꾼다
kubectl replace -f old.yaml                                         # Conflict: the object has been modified
kubectl delete configmap demo

# PostgreSQL 복제 지연
psql -h primary -c "SELECT client_addr, state, replay_lag FROM pg_stat_replication;"
psql -h replica -c "SELECT now() - pg_last_xact_replay_timestamp() AS lag;"

# 이 기계의 시계는 얼마나 어긋나 있나? (chrony 또는 systemd-timesyncd)
chronyc tracking            # "System time"이 NTP와의 차이다
timedatectl                 # "System clock synchronized: yes/no"

# 멱등 키를 붙인 재시도 (헤더 이름은 API마다 다르다)
curl -X POST https://api.example.com/orders \
  -H 'Idempotency-Key: 6f1c2a9e-order-42' -d '{"item":"book"}'
```
