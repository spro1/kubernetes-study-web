# 리버스 프록시와 로드밸런싱

서비스로 들어오는 요청은 대부분 코드에 닿기 전에 nginx, HAProxy, Envoy 같은 리버스 프록시를 지난다. 요청 하나를 L4 로드밸런서와 L7 프록시로 따라가며 백엔드를 어떻게 고르고 확인하는지, 어떤 헤더가 붙는지, 502와 504가 어디서 나오는지 본다.

## L4냐 L7이냐, 상태 코드마다 무슨 뜻인가

| | L4 로드밸런서 | L7 리버스 프록시 |
|---|---|---|
| 다루는 것 | TCP·UDP 연결 | HTTP 요청 |
| 보는 것 | IP와 포트(TLS 패스스루면 SNI) | 호스트, 경로, 헤더, 쿠키 |
| 정하는 시점 | 연결마다 한 번 | 요청마다 |
| 앱이 아는 클라이언트 IP | 모드에 따라 보존되거나 PROXY 프로토콜로 | `X-Forwarded-For`나 `Forwarded` 헤더 |
| 할 수 있는 것 | 어떤 프로토콜이든, 아주 빠름 | 경로 라우팅, 경로 변경, 재시도, 인증, 헤더 변경 |
| 예 | 클라우드 네트워크 LB, IPVS, HAProxy `mode tcp` | nginx, HAProxy `mode http`, Envoy, 클라우드 애플리케이션 LB |

| 프록시가 준 상태 | 뜻 | 흔한 원인 | 확인할 것 |
|---|---|---|---|
| 502 Bad Gateway | 업스트림이 거부·리셋하거나 잘못된 응답을 보냈다 | 앱이 죽음, 포트 틀림, 업스트림이 쉬던 keep-alive 연결을 닫음 | 앱 로그, 업스트림 포트, 유휴 타임아웃 |
| 503 Service Unavailable | 요청을 받을 백엔드가 없다 | 모든 백엔드가 헬스 체크에 실패, 또는 설정된 백엔드가 없음 | 헬스 체크 결과, 프록시 뒤의 엔드포인트 |
| 504 Gateway Timeout | 업스트림이 프록시 타임아웃 안에 답하지 않았다 | 느린 쿼리나 하위 호출, 너무 짧은 타임아웃 | 업스트림 응답 시간, `proxy_read_timeout`이나 경로 타임아웃 |

## 직접 확인해 보기

```bash
curl -sv -o /dev/null https://example.com/ 2>&1 | grep -iE '^< (server|via|x-cache)'   # 어느 프록시가 답했나
curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' https://example.com/           # 상태 코드와 전체 시간
curl -s -H 'X-Forwarded-For: 1.2.3.4' http://localhost:8080/ip   # 앱이 위조한 헤더를 믿나 (직접 만든 테스트 엔드포인트)
nginx -T 2>/dev/null | grep -E 'proxy_(connect|read|send)_timeout|keepalive|real_ip'   # 실제 적용된 nginx 타임아웃과 신뢰 설정
echo 'show servers state' | socat stdio /var/run/haproxy.sock   # HAProxy 백엔드 상태 (stats 소켓 필요)
curl -s localhost:9901/clusters | grep health_flags              # Envoy 관리 API: 업스트림 호스트별 상태
kubectl logs -n ingress-nginx deploy/ingress-nginx-controller | grep -E '" 50[234] '   # 인그레스 접근 로그의 502/503/504
```
