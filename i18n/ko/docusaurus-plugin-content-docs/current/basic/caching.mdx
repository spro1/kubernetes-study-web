# 애플리케이션 캐시는 이렇게 움직인다

상품 페이지 하나를 애플리케이션 캐시로 따라간다. **앱 → 캐시 서버 → 데이터베이스** 순서다. 미스가 캐시를 채우고, 쓰기가 캐시를 지우고, 메모리가 차고, 인기 키가 부하 속에 만료되고, 캐시 자체가 죽는 것을 본다.

## 캐시 패턴

| 패턴 | 읽기 | 쓰기 | 잘 맞는 곳 | 주의 |
|---|---|---|---|---|
| 캐시 어사이드(지연 로딩) | 앱이 캐시를 보고, 미스면 DB를 읽어 캐시를 채운다 | 앱이 DB에 쓰고 키를 지운다 | 읽기가 많은 대부분의 앱. 캐시가 죽어도 데이터는 잃지 않는다 | 미스나 재시작 뒤 첫 읽기가 느리다. TTL까지 낡은 값 구간이 있다 |
| 리드 스루 | 미스가 나면 캐시 계층이 앱 대신 DB를 읽는다 | 보통 라이트 스루와 함께 쓴다 | 읽어 오는 로직을 앱 코드 밖에 둘 때 | DB에서 읽는 법을 아는 캐시 라이브러리나 제품이 필요하다 |
| 라이트 스루 | 늘 채워진 캐시에서 읽는다 | 쓰기마다 캐시와 DB에 함께 쓴다 | 쓰자마자 읽는 데이터 | 쓰기가 느려진다. 읽지 않을 데이터도 캐시에 든다 |
| 라이트 비하인드(라이트 백) | 캐시에서 읽는다 | 지금은 캐시에 쓰고, 나중에 모아서 DB에 내린다 | 카운터처럼 쓰기가 아주 많은 곳 | 캐시에 썼지만 아직 내리지 않은 데이터는 캐시가 죽으면 사라진다 |

## 직접 확인해 보기

```bash
redis-cli SET product:42 '{"price":100}' EX 300   # TTL 300초로 저장
redis-cli GET product:42                           # 적중: 값을 돌려준다
redis-cli TTL product:42                           # 남은 초 (-1 TTL 없음, -2 키 없음)
redis-cli EXPIRE product:42 60                     # TTL 바꾸기
redis-cli DEL product:42                           # 쓰기 뒤 무효화
redis-cli SET lock:product:42 1 NX EX 5            # 스탬피드 잠금: 처음 부른 쪽만 OK
redis-cli INFO stats | grep -E 'keyspace_(hits|misses)|evicted_keys'   # 적중률과 축출
redis-cli CONFIG GET maxmemory-policy              # 메모리가 찼을 때의 동작
```
