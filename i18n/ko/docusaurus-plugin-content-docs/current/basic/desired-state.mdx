# 원하는 상태와 컨트롤 루프

쿠버네티스에는 "이것을 하라"고 지시하지 않는다. "이런 모습이어야 한다"고 적어 두면, 컨트롤러가 지금 모습과 끝없이 비교하며 맞춘다. 이 비교 순환과, 자원끼리 서로를 찾는 레이블·셀렉터를 따라가 본다. 부품 하나하나를 거쳐 파드가 뜨는 과정은 [파드가 뜨기까지](../k8s/pod-startup.mdx)에서 다룬다.

## 오해와 사실

| 흔한 오해 | 실제로는 |
| --- | --- |
| apply가 성공하면 파드가 다 떴다 | 원하는 상태가 기록됐을 뿐이다. 실제 상태가 따라오기까지 시간이 걸린다 |
| 자원이 모자라면 오류가 난다 | 오류 없이 Pending으로 대기하며 자리가 날 때까지 계속 시도한다 |
| status도 사용자가 고친다 | status는 쿠버네티스가 채운다. 사용자는 spec만 쓴다 |
| 서비스는 파드 이름으로 대상을 찾는다 | 레이블 셀렉터로 찾는다. 레이블이 맞는 새 파드는 자동으로 대상에 들어온다 |
| 셀렉터가 틀리면 저장이 거절된다 | 대상 0개인 채로 정상 저장된다 |

컨트롤 루프가 실제로 파드를 되살리는 장면은 [파드가 죽으면 (자가 치유)](../k8s/self-healing.mdx)에서 이어진다.

## 직접 확인해 보기

```bash
kubectl create deployment demo-web --image=nginx --replicas=3   # 원하는 상태 제출 (연습용)
kubectl get deploy demo-web                          # READY: 현재/원하는 개수
kubectl get deploy demo-web -o jsonpath='{.spec.replicas} {.status.readyReplicas}{"\n"}'   # spec과 status 비교
kubectl get svc <서비스> -o jsonpath='{.spec.selector}'   # Service가 고르는 레이블
kubectl get endpointslices -l kubernetes.io/service-name=<서비스>   # 엔드포인트가 0개면 셀렉터부터 의심
kubectl delete deployment demo-web                   # 정리
```
