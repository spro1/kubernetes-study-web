## 방식 고르기

| 방식 | 방향 | 전송 | 재연결 | 잘 맞는 곳 |
|---|---|---|---|---|
| 폴링 | 클라이언트가 물음 | 간격마다 새 요청 | 매번 새 요청 | 느리게 바뀌는 상태, 가장 단순한 구성 |
| 롱 폴링 | 클라이언트가 묻고 서버가 붙잡음 | 데이터나 타임아웃까지 열어 둔 요청 | 클라이언트가 다시 물음 | SSE나 웹소켓이 막힌 환경의 알림 |
| Server-Sent Events | 서버 → 클라이언트 | 긴 HTTP 응답 하나, `text/event-stream` | EventSource에 내장, `Last-Event-ID`로 이어 받기 | LLM 토큰, 실시간 피드, 진행률 |
| 웹소켓 | 양방향 | HTTP 업그레이드(`101`) 뒤 프레임 | 앱이 직접 | 채팅, 게임, 공동 편집 |
| gRPC 스트리밍 | 한쪽 또는 양쪽 | HTTP/2 스트림 | 앱이나 라이브러리가 재시도 | 서비스 사이 스트림 |

## 스트림이 끊길 때

| 증상 | 흔한 원인 | 해결 |
|---|---|---|
| 답이 한꺼번에 나타난다 | 프록시·게이트웨이·압축 계층의 버퍼링 | `proxy_buffering off` 또는 `X-Accel-Buffering: no`, `curl -N`으로 구간별 확인 |
| 1분쯤 조용하면 스트림이 멈춘다 | 어느 구간의 유휴·읽기 타임아웃 | 가장 짧은 타임아웃보다 자주 하트비트, 스트리밍 경로의 타임아웃 늘리기 |
| 웹소켓 핸드셰이크 실패, `101`이 없다 | 프록시가 `Upgrade`·`Connection`을 넘기지 않음 | 그 프록시나 로드밸런서에서 웹소켓 지원 켜기 |
| 배포할 때마다 스트림이 끊긴다 | 유예 시간이 스트림보다 짧음 | SIGTERM에 드레이닝, `terminationGracePeriodSeconds` 늘리기, 클라이언트 재연결 |
| 스케일 아웃 뒤 새 파드가 논다 | 긴 연결이 기존 파드에 고정됨 | 연결 수명 제한, 요청 단위 L7 분산, 최소 연결 |

## 직접 확인해 보기

```bash
# SSE 스트림이 도착하는 모습 보기. -N은 curl 자체의 출력 버퍼링을 끈다
curl -N -H 'Accept: text/event-stream' https://app.example.com/events

# OpenAI 호환 서버(예: vLLM)에서 토큰을 받으며 줄마다 시각 찍기
curl -sN http://localhost:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"my-model","stream":true,"messages":[{"role":"user","content":"Count to 20"}]}' \
  | while IFS= read -r line; do echo "$(date +%T) $line"; done    # 모든 줄의 시각이 같으면 버퍼링이다

# 프록시를 건너뛰고 파드에 바로 같은 요청을 보내 버퍼링 구간 찾기
kubectl port-forward deploy/chat-api 8080:8080

# 인그레스와 HTTPRoute의 스트리밍 관련 타임아웃
kubectl get ingress -A -o yaml | grep -E 'proxy-(read|send)-timeout|proxy-buffering'
kubectl get httproute -A -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.spec.rules[*].timeouts}{"\n"}{end}'

# 파드가 스트림을 드레이닝할 수 있는 시간
kubectl get deploy chat-api -o jsonpath='{.spec.template.spec.terminationGracePeriodSeconds}{"\n"}'
```
