# 서비스 호출이 장애를 견디게 하기

## 패턴과 놓을 자리

| 패턴 | 지키는 것 | 흔한 설정 | 주의할 점 |
|---|---|---|---|
| 타임아웃 | 호출한 쪽이 끝없이 기다리는 것 | 호출마다, 호출한 쪽 자신의 타임아웃보다 짧게 | 너무 길면 소용없고, 너무 짧으면 멀쩡히 느린 호출까지 실패한다 |
| 백오프·지터 재시도 | 잠깐의 실패 | 2~3번 시도, 무작위 폭을 섞은 지수 대기 | 멱등한 요청만, 한 층에서만 |
| 재시도 예산 | 재시도 폭풍에서 호출받는 쪽 | 재시도를 평소 트래픽의 일정 비율로 제한 | 예산을 다 쓰면 재시도가 조용히 멈춘다 |
| 서킷 브레이커 | 호출받는 쪽과 호출한 쪽의 시간 | 실패 비율이나 횟수, 쿨다운, 시험 호출 | 열린 상태에서 줄 대체 응답이나 분명한 오류가 필요하다 |
| 벌크헤드·풀 상한 | 같은 호출자의 다른 의존 서비스 | 업스트림별 최대 연결 수와 대기 요청 수 | 너무 작으면 평소 최고치도 거절한다 |
| 부하 차단·속도 제한 | 서비스 자신 | 429나 503에 `Retry-After` | 클라이언트가 따라야 의미가 있다 |
| 대체 응답 | 사용자 경험 | 캐시, 기본값, 나중에 처리할 큐 | 고장 난 부분에 기대면 안 된다 |

| 자리 | 예 | 잘하는 것 | 한계 |
|---|---|---|---|
| 클라이언트 라이브러리 | resilience4j, Polly, gRPC 재시도·데드라인 설정 | 어떤 호출이 멱등한지, 어떤 대체 응답이 맞는지 안다 | 언어마다, 서비스마다 따로 해야 한다 |
| 서비스 메시 | Istio `VirtualService`의 재시도·타임아웃, `DestinationRule`의 연결 풀·이상 감지, Linkerd 재시도와 예산 | 코드 수정 없이 모든 서비스에 같은 정책 | 업무 의미를 모른다. 대체 응답은 코드에 남는다 |
| 프록시·게이트웨이 | Envoy, nginx, HAProxy, API 게이트웨이 | 입구 한곳에서, 클라이언트별 속도 제한 | 자기 홉만 본다 |

재시도는 한 층만 고른다. 3번 시도하는 메시 앞에 또 3번 시도하는 클라이언트 라이브러리가 있으면 6단계의 재시도 폭풍이 된다.

## 직접 확인해 보기

```bash
# 호출 하나에 타임아웃: 연결 2초, 요청 전체 5초
curl -sS -o /dev/null -w '%{http_code} %{time_total}s\n' --connect-timeout 2 --max-time 5 https://example.com/

# curl 자체 재시도: 일시적 오류(타임아웃, 408, 429, 500, 502, 503, 504)에
# 1초 기다린 뒤 두 배씩 늘린다. --retry-max-time이 전체 시간을 묶는다
curl -sS -o /dev/null --retry 3 --retry-max-time 20 https://example.com/

# 서버가 보내는 속도 제한·Retry-After 헤더 보기
curl -sSI https://example.com/ | grep -i -E 'retry-after|ratelimit'

# Istio를 쓴다면: 서비스별 재시도, 타임아웃, 풀 상한, 이상 감지
kubectl get virtualservice -A -o yaml | grep -E -A4 'retries:|timeout:'
kubectl get destinationrule -A -o yaml | grep -E -A6 'connectionPool:|outlierDetection:'
```
