# PV 생명주기와 회수 정책

누군가 데이터베이스의 PVC를 지웠다. 디스크도 같이 사라질까? PersistentVolume 하나를 **Available → Bound → Released → (Failed)** 순서로 따라가며 회수 정책이 무엇을 정하는지 본다.

## PVC를 지우면 일어나는 일

| 정책 | PVC가 사라진 뒤의 PV | 클라우드 디스크와 데이터 | 다음 할 일 |
|---|---|---|---|
| `Delete` (동적 프로비저닝 기본값) | 삭제 | 삭제 | 치울 것도, 되살릴 것도 없다 |
| `Retain` (손으로 만든 PV 기본값) | `Released`, `claimRef` 유지 | 남음 | 관리자가 PV를 지우고 다시 만들거나 `claimRef`를 지운다 |
| `Recycle` (폐기 예정) | 볼륨을 `rm -rf`한 뒤 `Available` | 데이터 지워짐 | 대신 동적 프로비저닝을 쓴다 |
| 회수 실패 | `Failed`, 또는 경고 이벤트와 함께 `Released` | 알 수 없음, 스토리지 쪽 확인 | `kubectl describe pv`를 읽고 스토리지 쪽을 고친 뒤 PV를 지운다 |

| 증상 | 원인 | 해결 |
|---|---|---|
| PVC가 `Terminating`에 멈춤 | 파드가 아직 쓰고 있다 (`kubernetes.io/pvc-protection`) | 파드를 멈추거나 지운다. 필요하면 먼저 백업하거나 PV를 `Retain`으로 패치한다 |
| `Released` PV가 있는데 새 PVC가 `Pending` | Released PV는 다시 묶이지 않는다 | PV를 손으로 회수한 뒤 `claimRef`와 `volumeName`으로 미리 묶는다 |
| `volumeName`을 준 PVC가 빈 새 디스크를 받음 | `storageClassName`을 빠뜨려 기본 클래스가 적용됐다 | PVC와 PV 모두에 `storageClassName: ""`를 준다 |

## 직접 확인해 보기

```bash
kubectl get pv                                         # STATUS, CLAIM, RECLAIM POLICY, STORAGECLASS
kubectl get storageclass -o custom-columns=NAME:.metadata.name,RECLAIM:.reclaimPolicy
kubectl get pvc data -n shop -o jsonpath='{.metadata.finalizers}{"\n"}'   # ["kubernetes.io/pvc-protection"]

# PVC가 지워져도 디스크를 남긴다
kubectl patch pv pv-db -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'

# PVC가 지워진 뒤: Released, 옛 claimRef가 남아 있다
kubectl get pv pv-db -o jsonpath='{.status.phase} {.spec.claimRef.namespace}/{.spec.claimRef.name}{"\n"}'

# 다시 Available로 만드는 지름길 (옛 데이터는 디스크에 남는다)
kubectl patch pv pv-db --type json -p '[{"op":"remove","path":"/spec/claimRef"}]'
kubectl describe pv pv-db                              # Failed의 이유는 이벤트에 있다
```
