# KEDA로 이벤트에 맞춰 늘리기

큐 소비자는 메시지가 수천 개 쌓여도 CPU가 낮을 수 있다. **KEDA**가 밀린 양을 읽어 HPA를 움직이고, 0으로 줄였다 다시 깨우고, 큐에 닿지 못할 때 무엇을 하는지 따라간다.

## 동작을 바꾸는 ScaledObject 필드

| 필드 | 기본값 | 정하는 것 |
|---|---|---|
| `minReplicaCount` | 0 | 가장 적은 레플리카 수. 0보다 크면 활성화 임계값은 무시된다 |
| `maxReplicaCount` | 100 | HPA에 넘기는 가장 많은 레플리카 수 |
| `pollingInterval` | 30초 | 오퍼레이터가 트리거를 확인하는 간격 |
| `cooldownPeriod` | 300초 | 마지막 활성 트리거 뒤 0으로 가기 전까지 기다리는 시간. 1 → 0에만 쓰인다 |
| `initialCooldownPeriod` | 0초 | 만든 뒤 처음 0으로 가기 전까지 기다리는 시간 |
| `idleReplicaCount` | 없음 | 활성 트리거가 없을 때의 레플리카 수(0만 지원하고, `minReplicaCount`보다 작아야 한다) |
| `fallback.failureThreshold` / `fallback.replicas` | 없음 | 이만큼 폴링이 실패하면 이 수로 맞춘다 |
| `advanced.horizontalPodAutoscalerConfig.behavior` | HPA 기본값 | 1 ↔ N에서 늘리고 줄이는 속도 |
| 트리거의 `activation…`(예: `activationLagThreshold`) | 0 | 0에서 깨어나려면 지표가 이 값보다 커야 한다 |

## 직접 확인해 보기

```bash
kubectl get scaledobject -A                          # READY, ACTIVE, FALLBACK, TRIGGERS
kubectl describe scaledobject orders                 # 오퍼레이터가 남긴 조건과 이벤트
kubectl get hpa keda-hpa-orders                      # KEDA가 만든 HPA
kubectl describe hpa keda-hpa-orders                 # 현재 외부 지표 값과 확장 이벤트
kubectl get --raw "/apis/external.metrics.k8s.io/v1beta1" | head -c 400   # KEDA 지표 서버가 등록됐는지
kubectl get triggerauthentication,clustertriggerauthentication -A
kubectl get scaledjob,jobs -A                        # ScaledJob과 그것이 만든 Job
kubectl logs -n keda deploy/keda-operator | tail     # 스케일러 오류(네임스페이스는 설치에 맞게)
```
