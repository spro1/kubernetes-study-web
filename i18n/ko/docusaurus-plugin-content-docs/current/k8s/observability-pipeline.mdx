# 로그·메트릭·트레이스가 파드를 떠나는 길

파드 하나에서 나오는 신호 셋을 따라간다. **로그**는 stdout으로 나가 노드의 파일에 쌓인다. **메트릭**은 `/metrics`에서 프로메테우스가 당겨 가기를 기다린다. **트레이스**는 OTLP로 수집기에 밀어 보낸다. 길마다 끊기는 방식이 다르다.

## 세 신호 비교

| 신호 | 누가 옮기나 | 방향 | 어디에 남나 | 흔한 장애 |
|---|---|---|---|---|
| 로그 | 컨테이너 런타임이 파일로 쓰고, 데몬셋 에이전트가 보낸다 | 노드 파일에서 거둬 감 | 로그 저장소(예: Loki, OpenSearch) | 보내기 전에 파드 삭제, 회전 중 에이전트 지연, 앱이 파일에 로그 기록 |
| 메트릭 | 프로메테우스, 서비스 디스커버리로 | 당김(스크레이프) | 프로메테우스 TSDB나 원격 저장소 | 대상 다운(`up == 0`), 포트·경로 틀림, 카디널리티 높은 레이블 |
| 트레이스 | 앱 안의 OpenTelemetry SDK | 밀어 보냄(OTLP) | 트레이스 백엔드(예: Jaeger, Tempo) | 수집기 주소 틀림, 트레이스 컨텍스트 전파 누락, 샘플링으로 빠짐 |
| 리소스 메트릭 | metrics-server, 각 kubelet에서 | 당김 | 메모리에 최신 값만 | metrics-server가 없어 `kubectl top`과 HPA 실패 |

## 직접 확인해 보기

```bash
kubectl logs deploy/web --tail=50                    # kubelet을 거쳐 현재 컨테이너 로그 읽기
kubectl logs web-7c9d -c app --previous              # 직전에 죽은 인스턴스의 로그
kubectl get daemonset -A                             # 노드마다 로그 에이전트가 도는가?
kubectl debug node/worker-1 -it --image=busybox -- ls /host/var/log/pods   # 노드에 있는 파일
kubectl port-forward deploy/web 8080 &
curl -s localhost:8080/metrics | head                # 프로메테우스가 긁어 가는 내용
kubectl top pod -A                                   # metrics-server의 Metrics API
kubectl get servicemonitor,podmonitor -A             # 프로메테우스 오퍼레이터를 쓴다면
```
